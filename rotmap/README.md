# Ravages hex map — vector editor & travel calculator

Static site — works on github.io or locally with `python -m http.server` (file:// won't work, fetch is blocked).

## Files

- `index.html`, `app.js`, `style.css` — the app
- `rules.js` — all movement rules as data + cost functions (documented, edit to tune)
- `rules.md` — human-readable movement rules reference
- `data/terrain.json` — snapshot of the Google Sheet (4,230 grid positions, of which 4,113 are map; the sheet pads its grid three columns wider than the world and fills them with `N/A`, and nothing draws those — "Refetch sheet" pulls live). Each hex carries its terrain, stronghold/river/road flags and its **region** (`g`) — the sheet's Region column, 24 of them, covering every hex but the first
- `data/strongholds.json` — OCR'd stronghold names (18 unnamed — fix with the Label tool)
- `data/features.json` — *your* drawn overlay, including hand-painted realm colours and the names given to them; export from the app and commit it here
- `data/commanderies.json` — the **commanderies** (see below), derived from the three scans in `ref/` by `tools/build-commanderies.py`. Generated; don't hand-edit
- `tools/build-commanderies.py` — reads the commandery scans into that file. Needs Pillow, and only needs running when a scan changes
- `ref/` — classic map + old layer images, used only as tracing overlays. Two of them are **realm scans** rather than tracing aids: `Borders_clean.png` (who holds what by right) and `warlords.png` (who holds it now). Three more are **commandery scans**: `core_commanderies.png`, `provinces_commanderies.png`, `frontier_commanderies.png`

## Regions and commanderies

The map divides the same ground twice. A **region** is geographic — the Ayauda River Valley, the Mysi Coast — and comes from the sheet's own Region column, one name per hex, 24 of them covering everything. A **commandery** is administrative, and comes from the three scans: flat colour per commandery on the same canvas as every other ref image, one image per tier — **core**, **province**, **frontier**. 72 of them over 676 hexes, so most of the map is in none: Tarn, Nisaya, the Hyavā Shore and the Mysi Coast are conquest and frontier, not administered ground, and the scans say nothing about them.

Two things about reading the scans are worth knowing. Colours are **reused** between distant commanderies — two unconnected provinces are both pure yellow — so a colour is not an identity; each colour's hexes are split into connected components and every component becomes a commandery of its own. And flat grey `#a0a0a0` means "inside this tier's lands but in no commandery", which is dropped along with the transparent pixels.

A commandery **has no name of its own**. It is named for the grandest settlement it holds — a major city over a fortress over an ordinary stronghold, ties going to the lowest hex id — and that is worked out in the app from the live stronghold data rather than baked into the JSON, so renaming a stronghold with the Label tool renames the commandery around it, and promoting one to a major city can change which settlement the commandery is named after. Every one of the 72 currently lands on a distinct name. The capital's is a single hex.

## Workflow

1. **Draw mode** — pick a tool, click to place points. Points snap to hex corners, edge midpoints, centers and sub-centers (half-way points), so rivers can run along edges or through hex interiors, and roads can enter/exit any side. Alt = free placement, Enter/double-click = finish, Esc = cancel, Ctrl+Z = undo, right-click = finish. Turn on the "Classic map" / "Ref:" layers to trace.
2. Work autosaves to the browser. **Export JSON** → save as `data/features.json` → commit → github.io serves it to everyone.

   Which raises the question of what happens when a browser has both, and for a long time it was answered as a **choice** — one that was wrong half the time whichever way it went. Locally the browser's copy won, so a `features.json` pulled from someone else was invisible until the copy was thrown away by hand. On the published map the file won whenever it changed, so a reader who had named a dozen realms lost the lot at the next republication. Neither is what anyone wanted, and the reason is that it is not a choice: the copy in the browser and the file on the server are two descendants of the same parent, and what is wanted is both sets of changes.

   So the parent is kept. Beside the working copy sits **the file it was made against**, and when a new one arrives the three are merged. For every part of the drawing, whoever changed it since the parent wins; where both changed the same part the local edit is kept, because a reader's own work is the thing they will notice missing and the file's version of it is one republication away from arriving again anyway; where neither changed anything the parent's value passes through. Objects recurse, so two edits inside one hex collide only if they are to the same field, and anything that is not a plain object — a number, a name, a hex's list of stronghold markers — is atomic, which is right here: a marker list is one statement about that hex, and half of each side's would be a hex neither of them meant.

   The drawn lines are not merged that way, because a line has no key to merge under. They are matched by their whole content: what you end up with is the new file's lines, less the ones erased locally, plus the ones drawn locally. Editing a line in place therefore reads as an erase and a draw, which is what it is — a line here is a value, not a thing with an identity.

   The price is one more copy of the file in storage. What it buys, checked against the real 898-feature drawing: a label edited on both sides keeps yours, a label either side added arrives, a stronghold renamed on either side keeps that rename, a line you erased stays erased through a republication that still has it, and a file that changed nothing you touched comes through whole. A browser whose copy predates all this has no parent to merge against and falls back to the old rules exactly once, after which it has one.
3. **Route mode** — multiple routes, each with its own color (click swatch to cycle, double-click name to rename, × to delete). Clicks extend the *active* route. Right-clicking a hex already traversed by a route inserts a normal draggable waypoint into the leg that crosses it; a trade-route hop's internal hexes work too. Off the line, the same menu can append to the active route or start another one. Army composition and weather apply to all routes. Routes persist in the browser.

At the foot of the icon rail, above the collapse arrow, are the two switches that decide what survives a reload.

**Saving**, on by default, is the whole of the paragraph above in one button. Off means **nothing is written and nothing is deleted**: no autosave of the drawing, the board or the routes, no removals either, and at the next load the copies already in the browser are passed over in favour of the shipped files. So an afternoon of "what if he marched here instead" leaves at a reload and takes nothing with it, and the work that was in storage is still in storage — switch saving back on, reload, and it is there. Switching it *on* writes what is on screen at once rather than waiting for the next edit, or the browser would be claiming to save while holding something older. The switch itself is a preference about this browser rather than a change to the map, so it is kept whatever it says: it is the only thing that is.

**Reset map** asks before it acts, and asks beside itself: the first click unfolds an *Are you sure?* tab sideways out of the button, and the second click lands on that tab rather than on the button again, so a double-click cannot answer a question it never saw. The tab keeps the one wording whatever is at stake — what is at stake is already on the button's own hover label and in the colour it is wearing, and a slot that reworded itself would be asking to be read again every time rather than clicked. A second click on the button, a click anywhere else, Esc, or five seconds of nothing puts it away. A browser `confirm` would have greyed the whole map to ask about one rail button, which is louder than the thing it guards; the tab is animated on `max-width` so it wipes open from the button's own edge, and because the real width of it is its text, which an exact width would have to be measured for and would go wrong the moment the wording changed.

It puts the drawing and the board back to `data/features.json` and `data/tokens.json` in one gesture — the two panel buttons that each did half of this are still where they were — and it **lights amber when what is in front of you differs from those files**, and **greys out and stops answering when it does not**. That is a question about content rather than about whether anything has been touched: draw a road and rub it out again and the button goes grey again, where a flag counting edits would still be lit. Saying it with the button's own state rather than in words is deliberate — a live-looking button whose label explains that pressing it would do nothing is a sentence spent on a non-event — and going grey also disarms the tab, since a question asked about a state that has since gone back to the files has stopped being a question. The comparison is the two states as text with their keys sorted, since two objects holding the same map need not hold it in the same order; it costs about five milliseconds on a half-megabyte drawing and is deferred to the next idle moment, so no stroke ever waits for it. Routes and isochrone origins are deliberately left alone by the reset: they are planning laid over the map rather than part of it, no file ships with them, and their own Clear all is a click away. And a reset made while saving is off touches storage no more than an edit does — the switch means off in both directions, so a throwaway session cannot delete the work it was turned off to protect.

One bug fell out of writing the drift check, and it had been there from the beginning: with nothing in storage, `chooseFeatures` hands back the shipped object *itself* as the working state, so every edit was quietly an edit to the map's own idea of what it shipped with — and a reset then handed back the edited copy. The canon is now kept as text that nobody can draw on, and both the working copy and the reset are parsed out of it.

Drawing adds at most one hex per click (rejected clicks flash red) so features never skip hexes.

## Finding things

**Find is a surface over the map, not a panel**, and it answers to **Ctrl+F**. Everything else in the sidebar is something you settle into — plan a march, paint a border, place counters — whereas finding a place is something you do *while* doing one of those, and as a panel it made you leave the work to search and leave the search to get back. So it sits in the bottom-right corner, draggable, open beside whatever panel is in use, and it reopens where it was left. Ctrl+F is taken over from the browser deliberately: it is the key anyone already presses to find something on a page, and the browser's own bar would cover the map. Escape works in two stages, in this order — **clear, then close**: the first press empties the box and drops the selection, and only a second, with nothing left to clear, puts the surface away. Closing on the first press would take the panel down over a typo.

The Find box searches stronghold names, your own labels, region names, commandery names, **the counters on the board** — by designation and by commander alike — and bare hex numbers. A commandery answers to the name of the settlement it is named for, which is also a place in its own right, so typing `Cašman` returns two rows — the town, and the core commandery around it — with the town first and the commandery under it, labelled with its tier and its size. Names here are full of letters nobody is going to type — Naŕes, Hā-aēšema, Zakuruiôi, Sam'al — so nothing is matched as written: query and name are both folded to plain letters (accents dropped, case levelled, apostrophes and hyphens discarded) and then compared with a tolerance of a letter or two, counting a pair typed the wrong way round as one mistake rather than two. `nares`, `cashman`, `hasesema` and `kamabasin` all land on the right entry. Two- and three-letter queries are matched strictly, since anything looser matches half the map. Arrow keys move through the results, Enter takes the top one, Escape clears.

Counters are searchable because they are the one thing on this map that *moves*. Everything else Find knows about is a fixed feature of the ground; where a legion is changes week to week, so "where is V" was the lookup with no answer but scrolling the token list. Both of a counter's names work — "XII" and "Gautarza" name the same force — and whichever one matched is what titles the row, since that is the word you typed; the other is shown beside it, being the thing the row can tell you that you did not already know. A counter resolves to its **hex**, not to a selection kind of its own: the answer to *where is V* is a place, and making it a place means it lights up, pans and pins with everything else instead of needing a fourth branch through the selection machinery. It is keyed by its own id for deduplication, though, so a counter named after the town it is standing in gives two rows — the town and the force — which are two different answers to the same word.

What the search picks out is a **selection**, not a pointer: it stays lit until you drop it. A plain click selects one thing and drops everything else, moving the map to it — only moving, never zooming, since a search is for finding something rather than for deciding how closely you wanted to look at it. **Shift-click, or the +/− button on the row, adds** to what is already selected or takes that one back out, without moving the view, so you can build up a set of regions and hexes without being dragged away from what you were looking at. (The button exists because shift needs a keyboard; on a touchscreen it is the only way in.) The hex just picked blinks a few times before settling into a steady outline, which it needs now that the view no longer zooms in on it.

Selected rows are pinned to the top of the list with a ✓, and **they stay there when the box is empty** — a region selected three searches ago can still be found and switched off. Clicking the only selected thing switches it off; Escape drops the lot.

A selected region is washed gold and a selected commandery cyan — two colours because the two overlap everywhere and one of each can be lit at once, where a single colour would make a commandery inside a selected region read as the region having grown a brighter patch rather than as a second, smaller thing. A selected hex gets an outline. The wash covers whole hexes, water included: the sheet names a region per hex and that claim covers all of it, so a bay a coastline has cut out of a shore hex belongs to the same region as the hex around it. Its outer edge is drawn by stroking the same shape and masking away everything inside the region, which yields the silhouette without computing a union of several hundred hexagons and without any lines between two hexes of the region itself; each selected region keeps its own mask, so where two of them adjoin, the border between them still shows. The washes sit under the grid, roads and names so they tint the ground without burying it, while hex outlines go on the very top layer, where one thin hexagon won't be lost among the roads. Hovering any hex gives the readout: what it is called and its hex number, then its terrain and — where there is a stronghold — what kind of place it is as one phrase, **Port Major City**, **Inland Fortress**, and so on. *Port* rather than *coastal*, because coastal describes where a place is and port describes what it does — and it is the second that the map is asserting and the rules act on. A stronghold on the shore that ships cannot use is coastal and is not a port, which the old wording made unsayable; the flag has always meant the port, and the readout now says the same word the Stronghold tool and the marching rules use. Whether a stronghold can be reached by ship is the first thing anyone wants of it on a map with a fleet on it, so that leads rather than trailing in a bracket. Under that, a line each: the region, and the commandery with its tier in cyan. Then, from whichever realm scans are switched on, who holds the ground, with the realm's own colour as a chip beside its name — and **one line per answer rather than one per layer**. With both maps up the pair usually differ, a legion sitting on imperial ground, and saying so twice is the point of having both; but where they agree they agree because it is the same fact arriving twice, which is what happens over the Blue Scarves — they keep their own colour on the Borders map by construction, so both layers named them and the readout said it twice. Identical name *and* identical colour is the test, since the same name in two colours is a federation holding ground on both maps and still worth two lines. There is no "Borders"/"Warlords" qualifier: it was there to say which map a line came from, which sounds useful and is not, because the two are stacked deliberately so that what shows is who holds the ground now over who holds it by right — and what the qualifier actually did was put the machinery's vocabulary in front of the answer. Under all that, any counters standing on the hex, with their commanders' names.

The two are not read equally, because they were not drawn equally. The Warlords scan ships with a legend, so it names every colour it paints and admits it when it cannot. The Borders scan ships with none — twenty-five washes that would otherwise read out as hex codes, which tell a reader nothing — so **Borders speaks only where a colour has been named by hand**, and is silent otherwise. That silence is the default state of that map and is meant to be: name a wash once, with the palette's double-click rename, and every hex of that polity answers from then on.

There is one exception, and it is not a coincidence of colour: the realms in `BORDERS_INDEPENDENT`, which today means the **Blue Scarves**. Every other warlord is overlaid onto that map as the empire's own pale shade, because Borders is about who holds what *by right* and a legion holding imperial ground is still holding imperial ground. A realm in that set is nobody's subject, so `overlayWarlords` writes its own colour straight through instead — which means the colour is on the Borders map *because it is that realm*, by construction rather than by matching triple. The Warlords legend is describing it there rather than guessing at it, so it is allowed to.

Two things in the readout are scaffolding rather than world, and appear **only when the map is served locally**: which piece of a split hex the cursor is on (`· land subhex`), and the sheet's own river and road flags (`· river (sheet)`), which exist to check a drawn line against the data. The highlight still shows you the subhex either way; only the words are held back.

## On a phone

Below 820px the panel leaves the side of the map and becomes a sheet that slides up from the bottom, so the map gets the whole screen; a **Controls** pill opens it (carrying the active route's travel time so the headline number is readable with the sheet shut) and a **Remove last** pill in the opposite corner takes back a mis-tapped waypoint, since a touchscreen has no right button. Drag the sheet's handle down, or tap it, to dismiss. On the map itself, one finger pans, two fingers pinch to zoom, and a tap places a waypoint — with more slack for what counts as a tap than a mouse gets, and the taps as fingers lift after a pinch ignored. The map is 2.16:1, which would letterbox into a thin band on a portrait phone, so on touch screens the opening view is zoomed to cover the window instead, and reshapes to match when the phone is turned.

Everything the mouse can do has a way in by touch. **Press and hold** a hex to read it — the terrain, the stronghold, the region and the commandery — since a tap there means "waypoint here" and there is no such thing as hovering; the readout appears above your fingertip and goes away at the next touch. Keep holding and **slide**, and the finger becomes a cursor: the readout follows it from hex to hex instead of the map panning underneath, which is how you run along a row of strongholds without lifting off and holding again at each one. Panning is what a finger that hasn't waited does, so nothing is lost either way. Android raises its context menu from that same press, so a held finger never counts as the right-click that drops a waypoint. **Set origin** closes the sheet as it arms, because the next thing to do is tap the map, which the sheet was covering. Selections are built with the +/− buttons on the search rows rather than shift. Double-tap-to-zoom is off inside the sheet, so a double-tap to rename a route reaches the route rather than the browser.

**The Draw panel is on both maps; what is in it differs.** Published it keeps one tool — **Map painting**. Someone reading it may well want to move a front line on their own copy, and that touches nobody else's: it lives in their browser and travels only if they export it. The line tools, the Stronghold tool, **Label**, **Erase** and the whole **Data** panel are how the map itself is made, and are dropped — buttons and their help alike — rather than hidden. Which tools survive is marked in the HTML with `data-dev`, so the tool row and its help cannot drift apart, and the panel opens on whichever tool is left first: Road locally, Map painting published — armed, but it fetches nothing until it is clicked and paints nothing until a colour is chosen. Renaming and removing a stronghold do not go with the Label and Erase buttons: both are on the hex's right-click menu, which the published map keeps. The tools work by touch too (tap to place points, double-tap to finish, Undo in the panel), though the modifier-key refinements — Alt for free placement, **E** for snapping anywhere along an edge — have no touch equivalent.

**Borders** and **Warlords** are read rather than shown. Each is a scan of flat colour saying who holds what; the pixels are sampled per subhex — the thirteen grid points that fall inside the piece, plus its own interior point so a spit narrower than the gaps between them still gets a vote — and the land is repainted in whichever colour most of the samples agree on. A *subhex* is the unit, not a hex: two pieces of land in one hex, either side of a strait or a river, need not be held by the same realm and are asked separately. The result is flat colour per realm, so 4,000 hexes cost a couple of dozen SVG nodes. Land the scan doesn't speak for — a spit your own coastline puts further out than the scan's did — inherits from land it could be *walked* to. **Unclaimed neighbours vote too, for staying unclaimed**, and a realm has to outnumber the neutral ground strictly to take the piece. Counting only the claimed neighbours made a single claimed edge decisive however much of nobody's land the piece also touched — one vote beating nothing, because nothing was allowed to speak — so a spit adjoining one realm and two stretches of neutral came out as that realm's. A tie leaves it neutral: land is inherited when most of what it adjoins is held, not merely when something adjoining it is. A piece whose only land neighbours are claimed still inherits, there being nothing there to object, which is the case the pass was written for.

The pass **runs to a fixed point**, because a spit's nearest held ground is often another spit: the shore a drawn coast carves out runs as a chain of these fragments, and a single pass could only ever reach the first link. Hex 1965's sliver adjoined exactly two pieces of land, both Legion VI's in the finished map, but one of those was itself a blank the same pass was about to fill — so at voting time it counted as neutral rather than as the neighbour it turned out to be, one vote against one, and the sliver stayed grey between two red hexes. Each round now sees what the last one settled; in practice it converges after two, three pieces later. Within a round the gains are collected before being applied, so nothing inherits from an inheritance and the answer doesn't depend on the order the pieces are walked in. Iterating can't creep inland, because the only candidates are pieces of a *split* hex — a whole unsplit hex of genuinely neutral ground is never up for inheritance in any round — so what spreads stays confined to the shoreline the drawing itself created.

The Warlords scan has a **legend**, and hovering a hex names who holds that subhex while the layer is up — with the realm's own colour beside the name, so the readout and the ground can be matched without counting down a list. It says nothing when the layer is off, or over water, which holds no realm. The ten colours are sampled from the legend image rather than read off by eye, so the lookup is an equality test on the exact values in the file. The legend image lists ten; the scan holds an eleventh, `#00ff21` over about a third of a per cent of the map, which is Legion XII. All eleven are named in `WARLORD_NAMES`. A colour that ever isn't — a realm reaching the map before it reaches that table — is reported as unnamed with its value rather than guessed at or passed over in silence.

Either scan can be **painted on by hand**, with the **Map painting** tool — which is on the published map too, since a front line moves faster than anyone redraws a PNG.

Text entry, notices and destructive confirmations use the map's own dark dialog rather than browser `prompt`, `alert` or `confirm` boxes. The same surface covers realm, route, origin, token, commander, stronghold and free-map names; drawing and token resets; import failures; and the multiline clipboard fallback. Enter accepts a single-line entry, Escape cancels, and Ctrl/Cmd+Enter accepts multiline text.

**Reaching for the tool switches its layer on**, through the row's own checkbox rather than round the back of it, so the panel never claims a layer is off while the map is painting it. Both scans default to off, so before this the first few clicks landed invisibly and the tool looked broken.

**The first time that happens, the Layers panel opens with the row it ticked flashing three times.** A layer turning itself on has to be shown rather than done quietly, because the next question is always *how do I turn it off again* and the answer is then already on screen. Once only, though: it is a thing to be told, not a thing to be reminded of, and a panel that reopens whenever you reach for the tool — or switch scans, or come back from the eraser — is a panel you spend the session closing. The showing and the switching are separate for exactly that reason. The layer goes on **every** time; it is pointed at **once**. The flag is deliberately not saved with the UI preferences: this is orientation for whoever is at the map now, and a reload is cheap enough to be worth showing again. The scans are pictures of a moment and go out of date the way any picture does, so rather than repaint a PNG to move one hex, an override is kept per layer and per subhex and applied over whatever the scan said — after the sampling, after the spit inheritance and after the warlords overlay, since it exists for the places all three get wrong. The palette is whatever colours that layer actually uses, commonest first, read off the paint rather than kept in a list, so a realm added to a scan appears there on its own; warlord colours are named. Clicking the same colour again lifts the override and lets the scan speak; **Nobody** clears ground the scan claims, which nothing else can do.

Two entries in the palette are not colours, and wear a dashed outline rather than a chip so a row of solid swatches still reads as the palette. **Custom colour…** opens the native dialog to mix one the scan never used — a realm that did not exist when it was drawn — seeded with whatever is loaded, since mixing is nearly always an adjustment of something already on the map. A mixed colour joins the palette immediately and per layer, because the palette is read off the paint and a colour that is nowhere on the map yet is nowhere in that reading; once it has been laid down the reading holds it and the extra copy drops out. **Pick from map** arms a dropper — a mode the next click resolves, like the coast tool's sea-side pick, rather than a modifier, the one free modifier here being too close to the eraser's whole-line click. It reads what the map is *showing* under the cursor rather than what the scan alone said, since an override, an inherited spit and a warlord painted over the borders all look the same to the eye and must answer the same to the dropper; ground nobody holds picks up Nobody. Whatever it lifts is by construction already a swatch on screen. Escape disarms it, as does changing layer or tool.

**Clicking an existing entity's *swatch* recolours it**, replacing that colour across all the ground the entity currently holds. For Warlords, matching counters change with it, so Legion VI's land and tokens cannot disagree. Right-clicking the entity row offers the same recolour action, rename, and **Centre largest area**. The centre action pans to the middle of the largest contiguous piece, without changing zoom. Recolouring the realm and its counters is one undo step.

**Double-clicking a colour's *name* renames the realm** directly, while a right-click exposes the same action in a conventional menu. The Warlords scan ships with a legend of ten colours, identified from the image itself; the Borders scan ships with none, so its washes have only ever been able to go by their own hex code. A name given here is stored **per layer and per colour** and beats the legend, which turns the legend into a default rather than a fact — a legion that changes hands, a colour mixed for a realm that did not exist when the scan was drawn, and every unnamed Borders wash can all be told what they are. It is keyed by colour rather than by subhex, so naming one hex of a realm names the realm, and it shows in the hover readout as well as in the palette, since those are the two places a realm says what it is and they must not disagree. Clearing the text falls back to the legend and then to the hex, the same way clearing a stronghold's label falls back to the datasheet name. The names live in `features.json` beside the paint, so they export, import and undo with it. Dragging sweeps, and a sweep only ever sets — the click behaviour would flicker a subhex on and off as the hand wavered across it.

**The Borders map draws the warlords over the realms' own claims.** Its scan paints the empire in two shades of purple — sampled from the file rather than guessed at, being far and away its two commonest washes at 11% and 7% of the map. Ground a legion holds that the Borders scan does not already show as one of those two takes the **paler** shade: it is being held *from* the empire, and that map is about who holds what by right. The **Blue Scarves** are the exception, being nobody's subject — they keep their own colour and appear there as a realm in their own right. The overlay runs after the inheritance pass, so a spit that took its realm from the land beside it can still be overruled by a legion sitting on it, and it leaves the Warlords layer's own paint alone, which goes on saying exactly what its scan says. Switching Borders on reads the Warlords scan as a dependency, so none of this needs that layer to have been switched on.

The two differ only in what they are of. Borders' colours are semi-transparent washes and are composited onto white before use; the Warlords scan is flat and opaque and comes through that same path unchanged. Warlords leaves nine tenths of the map transparent, which needs no special handling — a transparent pixel is exactly what unclaimed ground means. **Warlords sits directly above Borders**, so with both on you see the warlord's claim and the realm beneath it only where no warlord has taken it, which is the comparison the pair exists to make.

## Commanderies are read per subhex

`data/commanderies.json` names whole hexes, because the scans it is read from are pixels over hexes and the Python tool that reads them has no idea where your coastlines are. But administered ground is **land**: a bay a drawn coast has bitten out of a shore hex is not part of the province around it, and saying so is the difference between a wash that describes a commandery and one that spills into the sea. So the hex list is refined in the app against the live geometry, and what comes out is a set of **subhexes**.

Refined, not re-derived. The alternative was to sample the three scans in the browser the way `paintRealm` samples the realm scans — the more faithful reading, since it could put two banks of one river in different commanderies — and it was rejected twice over. It means three more images fetched and sampled at boot, where the readout and the search want commanderies immediately and a JSON is free; and it would move the colour-to-component work out of the tool, where it is done once and can be inspected and versioned, into work redone on every load. The hex list is the identity. The coast is the only thing the tool could not know. This adds exactly that.

Two rules. **Water is not administered**: a sea subhex of a listed hex is left out. The test is `regWalkable`, which is exactly right — it admits land, and admits the water of a major river's channel where one splits a hex, since a reach running through a province is inside it, while leaving open sea out. It was `regWalkable || riverInRegion` at first, and that second clause quietly let nine **river mouths** in: a bay a drawn river empties into is reached by that river and is still the sea. The channel is in; the mouth is not. And **a sliver the list does not cover inherits**, by the same fixed-point pass the realm scans use — a spit your coast pushed out past what the scan drew belongs to the commandery it can be walked to, and a chain of such slivers resolves because each round sees what the last one settled. The pass is confined to `S.adj.sub`, the hexes a drawn coast or river actually cut, so nothing creeps across whole hexes of unadministered ground; and a piece stays out when the unadministered ground it touches outnumbers the province, because being in no commandery is a real answer about a piece of ground — most of this map is in none.

676 hexes come out as 774 subhexes, none of them sea. Three consequences worth knowing. The readout answers for the **subhex under the cursor**, so a bay says "no commandery" while the land beside it names the province. The wash is built from `regionShape` rather than whole hexagons, so it stops at the water's edge — a region's wash still covers whole hexes, and should, because the sheet names a region per hex and that claim covers all of it, but a commandery is administered ground read off a picture of the coast and the water is not its. And the **size** in the search rows counts ground rather than hexes touched, so a shore province half of whose hexes are water is no longer credited with the water; that number can now differ from the length of the hex list, and should — the list says which hexes it reaches into, this says how much ground that comes to.

## The commanderies as a layer

They are also a **layer of their own**, sitting between Borders and Warlords with its own row, slider and **A** button — labels on by default, since a wash of seventy-two colours nobody can name is a puzzle rather than a map. Above Borders because a province is the finer division and would be buried under the realm; below Warlords because what a legion holds this month should read over the administration it is being held from.

Unlike its two neighbours it is **not read off a scan**. Everything it needs is already worked out: the subhex sets above, and a name each, taken from whichever settlement the province holds. The one thing the data has no opinion about is colour — the scans it came from reuse the same yellow for provinces a thousand miles apart, which is why the tool splits them into components in the first place — so a colour is **made from the name**, FNV-1a over the letters into a hue, with saturation and lightness taking a narrow band so that seventy-two colours differ in the one way an eye can sort at a glance rather than in three ways at once.

Hashed rather than handed out in order, which buys three things. A province keeps its colour when another is added, split or renamed, because nothing depends on position in a list. The same province is the same colour in two browsers a week apart, with nothing stored anywhere to make it so. And renaming the settlement recolours the province, which is honest: on this map that *is* renaming the province. Two names hashing to the same colour would be painted as one province and labelled once, so a taken colour is stepped 37° around the circle until it is free — 37 being coprime with 360, so every hue is tried before any is repeated.

The labels come free. The realm-name fitting is written against a map of subhex → colour and a colour → name lookup, which is exactly what this layer produces, so commandery names are laid across their ground by the same pass that lays realm names across theirs — one collision list for all three layers, each label drawn into its own group so it comes and goes with its own switch.

**A name belongs on ground that is showing the colour it names.** The three washes stack — Borders, then Commanderies, then Warlords — so a layer's cells can be buried by a layer above it, and a commandery lying wholly under a warlord's wash was still having its name written across him: lettering that says the ground is one province's while every pixel of it says otherwise. Each layer's label pass now drops the cells a *visible* layer above it is painting. Partly covered, the name is refitted to what is left, which falls out of the design for nothing — the fitting takes a set of cells and asks no questions about where they came from, so cutting the set is the whole of it. Where too little is left to write on legibly the fitting declines and there is no label, which is the right answer for a province with nothing of itself in view. Switching any of the three washes therefore refits every label on the map, not only its own, and the refit is guarded on the switch having actually flipped — `apply` also runs on every frame of an opacity drag. Visibility only, not opacity: a wash dimmed to a quarter is still that layer's answer showing through, and reading a threshold off the slider would refit sixty times a second while it was being dragged. They are last in `RN_LAYER_ORDER`: where a province and a realm want to write the same word over the same ground, the realm is the larger claim. A commandery holding no named settlement is still painted, from its tier and index, and still labelled with nothing, because there is nothing to write.

The layer is off until asked for and repaints on the same beat as the scans — a coastline redrawn moves which subhexes are administered, and a stronghold renamed renames the province around it — but only while it is visible, since until then there is nothing on screen to be stale.

## Painting by the province

The Map tool paints a subhex at a time and a sweep paints a stroke, which is the right grain for a frontier and the wrong grain for the commonest edit of all: a province changes hands. Seventy-two commanderies is the administrative map the scans already draw, so "this one is his now" is one instruction — and doing it by hand meant nine or ten strokes and a squint at the boundary.

So the Map tool has a **right-click menu**, and it is there only while that tool is in hand. Everything the tool could do lived in the panel or on the pointer; what a right-click is for is acting on *what you are pointing at*, and the entries are exactly that — this subhex, and the province it is part of. Two entries, **Paint** and **Paint commandery**, and neither says which colour. The menu opened with the loaded colour named and swatched on both, and a palette flyout beside each so another could be chosen — one reading of "colour" too many. The colour is loaded in the panel, the panel shows it, and by the time you are right-clicking the map you have already chosen it: repeating it here was the tool telling you what you had just told it, twice, and offering to ask again. What the menu is for is *where* the colour goes — this subhex, or the whole province — so that is all it says. The commandery entry appears only where there is a commandery, since otherwise it is an entry with no subject. Undo and the clear are in the menu because a painting tool wants them within reach of the hand that is painting, not across the window.

Painting a province covers every subhex it holds, from the subhex reading — so it stops at the coast, and the bay in a shore hex is not painted with the land. It is **one undo step for the lot**, because it is one decision: nine subhexes go on, one Ctrl+Z takes all nine off. Painting the same province twice replaces rather than accumulates.

## One palette, and it is the warlords'

Everything that **stands on** the map and needs telling apart draws from a single list of twenty colours: the counters and the isochrone origins. One list rather than two, because two meant a counter and an origin could be "the same colour" without matching, and meant learning the swatch grid twice. Routes were once handed out of it as well and are not any more — a line has the opposite requirement to a counter, and that is a section of its own further down.

The list **is the Warlords legend**, behind five spares. Fourteen of the twenty are the legions in numeral order, each in the colour that scan paints its ground, so a counter and the territory under it are the same colour — which is the point of aligning them: a glance at the board says whose army is standing on whose land. Then the Blue Scarves, who are on both realm maps in their own right and so have a colour to match.

**The spares lead.** The first colour offered to a thing that is not a legion should not be a legion's: these fifteen mean something on this map, and a baggage train wearing Legion VII's green is a counter that reads as Legion VII's. Handing out and reading are allowed to disagree where there is a reason — a new **isochrone origin** is offered the strong hues first, because its colour is drawn as a thin outline around the ground it claims and the two quietest spares, near-white and charcoal, are the two worst lines to draw over this map. Its picker still shows the same grid as everything else.

The ten legions that hold ground on the scan take their colour from it, derived from `WARLORD_NAMES` rather than copied out of it so the two cannot drift. **Four legions hold nothing there** — IV, VIII, X and XI — so that scan gives them no colour and one is chosen here, in the hue gaps the other ten leave: the scan covers red, crimson, wine, orange, gold, tan, brown, two greens and a blue, which leaves teal, violet, olive and a desaturated slate. Legion XI's is deliberately the flat one; with thirteen saturated counters on a board, a grey among them is easier to pick out than a fourteenth hue squeezed between two others.

Twenty rather than fifteen because fourteen legions took all but one of the old fifteen and left nothing for anything that is not a legion — and because twenty is four even rows of five in the swatch grid where fifteen was three. The five spares are kept clear of all fifteen warlord colours *and* of the terrain beneath them (no mid-green for Flatlands, no tan for Hills, no grey-brown for Mountains, no soft mid-blue for Sea and Lake), so nothing among them can be mistaken for a legion or lost against the ground.

A counter's **rim** is black or white and nothing else, and a click on the counter swaps it. Two states rather than a colour, because the rim is not carrying information — the fill does that — it is carrying *contrast*, and against this map's terrain there are only two useful answers. Which one a counter starts with is worked out from its own fill by the same `inkOn` the numeral inside uses, so it is legible the moment it is made; the click overrides that, because the automatic answer is about the counter alone and cannot know what is underneath it. A brown counter on brown ground wants the white rim it is given; the same counter moved onto pale flatland wants the black one, and only the eye at the map can say so. A click used to step the *fill* through the palette, which stopped being a useful thing to do to a counter once the fill meant something — it turned Legion V into Legion VI's colour at a stray click. The fill is now changed deliberately, from the menu.

A counter's own menu entries appear only while the **Tokens panel is open**. They used to appear whenever you right-clicked a counter, which sounds helpful and is not: a counter sitting on the hex you want to march from is already in the way, and a menu that opens with six ways to rename and recolour it — above the hex entries you were after — makes it more so. Having that panel open is the plain statement that counters are what you are working on; with it shut, the counter is scenery and the hex under it is the subject. The panel's own rows answer the right button either way, and `Mark as` on the hex menu is how a counter gets made in the first place. There is no rim entry in that menu: a click on the counter swaps it, which is the whole of the feature, and a row saying so was a line spent on something the more obvious gesture already does.

A counter can also carry a **commander**: an optional full name, set from its menu and shown in the hover readout. The counter itself carries a *designation* — V, XII'a — because that is what has to be readable from across the map, and a designation is short; whose command it is is a different kind of fact, asked about one counter at a time, so it belongs in the readout rather than on the board, where fourteen names would bury the terrain. Blank is a real answer rather than a gap: the Blue Scarves are not anybody's command.

A counter's colour then **follows its label**: a token called V is Legion V and takes Legion V's colour, and so does its detachment V'a, since a detachment is part of its parent and colouring it separately would say otherwise. Two counters of Legion V are the same colour, because they are the same legion — the legion case is deliberately not subject to the "first unused colour" rule that governs everything else. A counter named anything else is offered the **spares first**: the fifteen warlord colours mean something on this map, and a baggage train wearing Legion VII's green is a counter that reads as Legion VII's.

One consequence had to be dealt with. A counter is now the same colour as its own ground, so the rim is the only thing making it a counter rather than a patch — and the rim was a fixed dark line, which is no rim at all on Legion II's navy or VI's wine or I's brown. It now contrasts with the counter's own fill, using the same `inkOn` decision the numeral inside uses, so the edge and the digit never disagree about which way round the contrast goes.

The shipped board in `data/tokens.json` is recoloured to match — and a browser that already has a board is brought up to the new colours too, because the shipped board only ever *seeded* an empty browser and every existing board went on showing the old palette. That is the same shape of fault as a stale features file shadowing a republished one, and it gets a narrower version of the same fix.

Narrower because only the **colours** are the map's to say. Where the counters are is the reader's own — a position played for a month must survive a republication — so the pass moves nothing. What colour Legion XII is, on the other hand, is not a matter of opinion: the label names a legion, the map paints that legion neon green, and a white counter labelled XII is simply out of date. So a counter whose label names a legion is set to that legion's colour, positions untouched, counters with any other label untouched. It is keyed on a fingerprint of the shipped board, so it runs **once per publication** rather than on every load, and it is a real undo step rather than a quiet one: one Ctrl+Z puts the old colours back for anyone who preferred them. **Starting positions** still reloads the shipped board wholesale for anyone who wants the positions as well.

## Realm names, fitted to the ground

The **A** button on the Borders and Warlords rows writes each named realm across the land it holds, the way the grand strategy maps do it: not a caption pinned to a centre, but lettering that runs the length of a country and bends with it, so the shape of the word tells you the shape of the country before you have read it. Off by default, since the layer is already colouring that ground and the lettering is a second answer to a question you may not be asking. Only **named** colours appear — the Warlords scan ships a legend and the Borders scan does not, so most of that palette has never been anything but a hex code, and writing `#DA85FF` across half the empire is not a label. Name a wash with the palette's double-click rename and it turns up here, which makes the switch a third reading of the same names the swatches and the readout give rather than a third place they could disagree.

The work divides in two, and that division is the important thing about it. **Finding a baseline** — a line through the country to write along — is a question with several defensible answers and no obviously right one. **Setting a name along a baseline** — trimming it to the ground, deciding how large the letters may be, how far apart, where they start — is the same problem whatever line arrived, and is answered once. So the baselines are a *list* rather than a decision, chosen from and tuned in the local-only **Realm labels** panel described at the end of this section, and everything downstream of `setNameAlong` neither knows nor cares which one it got.

Five steps, each answering a question the one before it raised.

**Whose ground.** Grouped by **name**, not by colour, which is the whole mechanism for a **federation**. Several washes given the same name are one polity: their subhexes go into one set, contiguity is worked out over the union, and what comes back is a single name laid across the whole of it rather than one copy per member. A confederation whose members each have their own colour on the scan — as a scan of *who holds what* quite properly draws them — then reads as the one thing it is. Name four of the south-western washes "Lasiŕos Federation" and one label arcs across all four.

Grouping by the name rather than by some separate notion of a group is deliberate. Naming is already the mechanism: stored per layer and per colour, exported, imported and undone with the rest of the hand-drawn work, and renamed by double-click in the palette. So there is nothing to invent and nothing new to keep in step. The tooltip goes on answering with the federation's name over any of its members, which is the right answer to *who holds this*, and the palette keeps the member swatches separate, which is the right answer to *what can I paint with* — it says in its tooltip how many colours share the name, since nothing else on screen would show that two of them had been tied together. For the treatment that inks a name in its realm's own colour, a federation's label takes the colour of the member holding most of **that block**, per block rather than per federation: the point of a federation is that its parts are elsewhere, and a name on one member's ground drawn in another's colour would be pointing at the wrong place.

**Which ground.** Those holdings are split into contiguous blocks, because a realm with an overseas province is two places and one label stretched between them would cross the sea. Contiguity is the *marching* kind — the same subhex adjacency the columns use, plus the two banks of a river within one hex — so a spit that can only be reached by boat starts a block of its own rather than being lumped in with the shore it happens to lie beside. The graph that answers this is kept rather than thrown away, because the spine below runs along the same edges.

**Which way the word runs.** The principal axis of the block, from the weighted covariance of its subhex centres: the direction the country is longest in is the direction a name wants to run. Weighted by **area**, not by count, or a coastline chopped into twenty slivers outvotes the solid interior behind it and drags the axis out to sea. A block with no clear long direction is given horizontal rather than whatever the arithmetic settled on, since for a circle the answer is noise — the test is the ratio of the two eigenvalues. And the tilt is capped at fifty degrees: past that a label stops reading as text on a map and starts reading as text turned on its side. The axis is **not** what the name is written along. All that is taken from it is where the country runs out in that direction — its westmost and eastmost subhex, which become the two ends of the spine.

**The spine.** The name is written along the *cheapest walk between those two ends, through the block itself* — Dijkstra over the block's own graph, where each step is priced by the distance it covers and then marked up by how close to an edge it lands. This replaced a least-squares parabola, which was a good description of a lobe and a bad one of a country. A realm shaped like two lobes joined by a two-hex neck has no parabola through it at all: the fitted line left the land at the neck, and the trim below then cut the name back to whichever lobe it had started in, leaving the other unnamed. A **walk through the block cannot leave the block**, so where the ground goes through a bottleneck the lettering goes through it too, which is the whole point. The pull towards the middle is a cost rather than a constraint, and that matters — a detour of one subhex to stay inland is worth taking, five is not, and at a neck there is no detour to be had so the walk simply threads it.

Endpoints along the axis rather than by graph diameter, incidentally, because graph-farthest sounds right and is wrong for a broad country: the two ends of the longest walk across a wide block are opposite *corners*, so the empire's name came out set on the diagonal.

**Calming it.** A walk on a hex grid staggers — every second step shifts half a hex sideways — and lettering set along the raw walk visibly ripples. Averaging and corner-cutting were tried first and are not enough: they reduce the amplitude without changing the fact that the line is still *following* every accident of the walk. What is wanted is a line that keeps the spine's **route** — which lobe, through which neck, bending which way — and forgets its detail, which is a low-order least-squares fit. The parameter has to be **distance along the spine**: fitting one coordinate against another is the old parabola again and cannot describe a shape that doubles back, which is exactly what a spine through a bottleneck often is. Fitting `x(s)` and `y(s)` **separately**, each as a cubic, has no such limit — the curve may hook or fork back as the ground does — while a cubic simply has nowhere to put a ripple. Three is the highest degree used: a cubic manages one real bend and the start of a second, which is as much as any country needs and one less than it takes to look nervous. A fitted spine that still turns more than three hundred degrees is thrown out rather than drawn, and *that* is when the old parabola comes back, as the fallback it should have been all along.

**Where it starts and stops.** The line is then *probed against the ground* — walked end to end, asking at each of a hundred steps which subhex it is over — and trimmed to the longest run that stays inside the block. A walk between cell centres is inside by construction, but the fit cuts corners and the ends are pushed out past the last centre to reach the coast, so the check still earns its keep, and it is what makes the parabola fallback safe to use at all.

With a **tolerance**, and that tolerance is what actually carries a name through a bottleneck. Calming the spine and threading the neck pull against each other: the walk goes through the neck, and then the cubic fitted to it cuts the corner and steps off the land for a sample or two on the way past. Judged strictly, that ends the run — so the empire's name was cut back to whichever lobe it started in and its own eastern half, four hundred hexes of it, went unnamed. A gap of a step or two is the smoothing showing, not the country ending, and the letters standing over it have a halo behind them. A gap of ten is the sea. Four steps is where this stops mattering, arrived at by measuring: at two the empire's name stops at the neck, at four it reaches the far end of its block, and **every value from four to twelve gives the identical answer**, so it is a plateau rather than a number tuned to one case. The shipped setting is well up that plateau, because the baseline that ended up as the default is a firmer shape than a fitted curve and leaves the land for longer where a country turns.

Then the size, which is settled together with the extent because each is the other's constraint. Two things bound it, and which of them bites is what gives the labels their character. The **length** of the surviving run bounds the name from the side — it cannot be wider than the country is long. The **thickness** of the country bounds it from above and below, measured by stepping out along the line's own **normal** (not the axis: on a bent label the two differ, and it is the normal that answers how much room the letters standing at this point have). Thickness is sampled as a **profile** the whole way along rather than as one number in the middle, because the two things it is wanted for are different questions.

The first question is how big the letters can be, and the answer is taken at the **35th percentile** of the profile rather than the median: a name has to fit the narrow places it crosses, not the average of narrow and wide. When length binds, the name comes out small and tight; when thickness binds, it comes out as large as the country is thick and the slack goes into **letter-spacing**, which is why the long thin realms end up with the wide-tracked lettering that reads as a map rather than as a caption. Tracking is capped at half an em: some of it is the whole look, but past a full em the gaps are wider than the letters and "IMPERIAL CORE" reads as thirteen separate capitals.

The second question is where the name may start and stop, and the answer is the profile **at those points**. A country tapers, and the run the trim hands back reaches into the point of the taper — the centreline is inside the country right to the tip, but the letters standing at the tip are a whole font size tall and there is no country left to hold them. Legion V's name ran down a spit and dropped its last letter in the sea for exactly this reason. So the ends are cut back to where the ground is thick enough to stand a capital in, which cannot be done before the size is known, and the size depends on how much run is left after cutting. Three passes, shrinking only, so it settles rather than oscillating. Within what survives the ends can be held back another half glyph, since the trim only ever followed the centreline.

Both of those end protections ship **off**, and that is a consequence of which baseline won. They were written for a fitted curve, which will run a name right into the point of a spit; an arc through the spine stays much closer to the middle of the ground, so the letters do not need holding back and the map reads better for the extra room. They are two sliders away if a name starts hanging off a headland again.

Which way round to read it is decided by the **x** component of the baseline and almost nothing else: a textPath sets glyphs from the start of the path onwards, so any net leftward drift is reversed however steep the line is. Only when the drift is genuinely vertical — under a fifth of the rise — does the sign of x stop meaning anything, and then the convention is top to bottom. This was wrong at first in a way that is not subtle: the rule compared `|dx|` against `|dy|` and left anything steeper than 45° to be decided by `dy` alone, so a coast running down-and-left at sixty degrees was judged "mostly vertical", found to be heading downwards, and set mirrored.

Bend is capped, on top of everything above and whatever baseline produced the line, as **sag against span** — the deepest the line falls away from the chord joining its ends, over the length of that chord. This is not the same test as the total turn: a long gentle curve turns a long way and reads perfectly, while a short sharp one turns very little and reads as a name falling over. Small blocks are where it bites. Twelve subhexes of Blue Scarves gave the fit an almost circular arc to work with, quite correctly, and the name came out bent double round it. The correction squashes the whole line towards its own chord rather than clipping the middle out of it, so what comes back is the same shape more shallowly drawn and still follows the country. Measured on the finished lettering, somewhere around a seventh is where a small block stops bending its name double and a genuinely curved country — the Tribes of the Neck — still visibly curves.

Widths are measured on a **canvas** rather than by asking the SVG. The honest way is to put the text in the document and read its length, but these labels are fitted while their group is switched off, which is the whole point of building on demand, and a hidden element has no length to give. The same family, weight and size measured on a canvas is the same font.

Finally the labels are **placed** rather than merely drawn, and placed for **both layers at once**. Two realms meeting along a narrow front each put their name near that front, and drawn as they came the pair sat on top of one another and neither could be read — the fitting knows about one country at a time and cannot see this. So candidates are taken biggest first and each is kept only if it does not touch one already placed, which resolves the collision in favour of the larger realm. The smaller label is **dropped rather than nudged**: a name shifted off its own ground to make room is worse than no name, since it is then labelling somebody else's country.

Placement cannot be a per-layer question, and treating it as one produced two faults the moment Borders and Warlords were both switched on. Each laid out its own names in ignorance of the other's, so a legion's name and the name of the imperial ground it sits on were written across each other; and the **Blue Scarves**, who appear on *both* maps — being nobody's subject they keep their own colour on the Borders map instead of being coloured in as the empire's — had their name written twice in the same place, once from each layer. So the candidates from every visible name group go into one pool and one pass places them, which gives two rules:

- **The two layers respect each other as if they were one.** One collision list, so a warlord's name and a realm's name give way to each other rather than being written across each other. They are allowed *nearer* than two names on one layer, though: on one layer two names close together is a real ambiguity about who holds the ground between them, and across the pair it is not, since the two are answering different questions about the same ground and a reader with both up is expecting them layered.
- **A name is written once.** If the same name has already been placed *from another layer*, this copy is dropped — only from another layer, since within one layer a realm may quite properly have its name on several separate pieces of itself, which is what the blocks-per-realm setting is about.

**Who wins is a precedence, not a size contest.** Sorting the joint pool by area was the obvious thing and it hands the map to Borders: the pale imperial wash is the largest thing on it by a wide margin, its name is set across three hundred hexes, it crosses half the legions on the way, and four legion names vanished under it — Legion XIV among them, on ground the map was painting as Legion XIV's. Which is backwards for a reader who has just switched Warlords on. With both layers up, the paint you can *see* inside a legion's territory is the legion's, Warlords being drawn over Borders and leaving the realm beneath showing only where no warlord has taken it. **The name should match the paint.** So the upper layer goes first regardless of size, and with that all eleven warlord names are drawn where before seven were. The rule is a control, since the opposite case is arguable: Warlords first, Borders first, or the old largest-wins.

**And a label that loses yields size before it yields existence.** Rather than being dropped outright, it is refitted smaller — two steps, and no further, since a name at a third of the size it asked for is unreadable rather than modest — and placed if it now fits. Smaller rather than nudged aside, because nudging moves a name off its own ground onto somebody else's, while shrinking keeps it where it belongs and says something true about the relation: the crowded name is the lesser claim on that ground.

Each label is still drawn into *its own* layer's group, so it goes on appearing and disappearing with that layer's switch, and switching a layer off hands back whatever it had ceded: Borders draws 25 names alone, 15 with Warlords up, and 25 again when Warlords goes down.

Because the pass is joint, switching either layer rebuilds both. That rebuild is guarded rather than unconditional, since the same handler runs on every frame of an opacity drag and refitting there would refit sixty times a second; it fires when a group's visibility actually flipped, or when a visible one is still empty.

What "touch" means here had to be fixed too. The test was overlap of bounding boxes, which is close enough for a level label and hopeless for a slanted one: the bounding box of a name set on a diagonal is mostly the two corners it does not touch, so one long diagonal claimed a quarter of the map and every small realm near it lost its name to a collision that was not happening — Olbi and Legion II both went that way. What a label occupies is a **ribbon** along its baseline, so each label now carries a chain of points down the middle of its lettering, and two labels touch when any pair of their points is closer than the two half-heights added together. A couple of hundred squared distances per pair, for pairs that are usually nowhere near each other.

A realm gets its name on each piece of itself but not on every scrap — at most three, and a piece must clear both a fifth of the realm's largest block and three whole hexes. Both tests are needed: without the fraction a large realm has its name written again on every coastal fragment it owns, and without the floor a realm that is *entirely* fragments ends up with no name at all.

The lettering is **opaque**, ivory on a solid dark rim, the halo scaled with the font so it stays a rim at every size instead of swallowing small labels and vanishing on large ones. It was translucent once — four fifths on the fill, three quarters on the halo — on the theory that the realm colour reading through would tie the name to its ground. What that actually did was mix every name with whatever it lay on and turn the lot grey, which is the one thing lettering on a map must not be: a label is either legible or it is dirt on the picture. The realm colour ties the name to its ground by being *underneath* it.

### The tuning panel

Which baseline is right, and what every threshold in the fitting should be, are not questions this file can answer by reasoning. They are answered by looking at a real map with real names on it and changing one number at a time — so there is a **Realm labels** panel, local only, and every number the fitting uses lives in one object (`RN`) with a control on that panel. It is built from a table rather than from markup, one row per knob, so adding a knob is adding a line and the panel cannot drift out of step with what it sets. The sliders answer live, since the whole value of the thing is watching the map move as you drag; a refit is around twenty milliseconds and the browser coalesces what it cannot keep up with. The published build has neither the panel nor the stored settings, and takes the defaults — which are what the panel was used to settle on.

The panel also reports what the last fit *did*: how many labels were drawn, how many were dropped for collisions, how long it took, and which algorithm each drawn label came from. That last matters because the interesting failures here are silent — a baseline that returned nothing and quietly fell back, or a label dropped for a collision, both leave a map that merely looks a bit bare.

Eight baselines, and they are genuinely different opinions rather than refinements of one another:

| Algorithm | What it does |
| --- | --- |
| **Straight — principal axis** | A level line along the block's long direction. The thing to compare the rest against: a curve that is not visibly better than this is not worth the arithmetic. |
| **Parabola on the axis** | The original. Describes a lobe well and a country badly; still the fallback, since whatever else fails, a country has an axis and a bend about it. |
| **Best-fitting circular arc** | A circle through the subhex centres by the algebraic (Kåsa) fit — `x²+y² = Ax+By+C` is linear in A, B, C, so the centre and radius fall straight out and it cannot fail to converge because it does not converge, it solves. One curvature for the whole label, which is calmer than a cubic and blinder to the shape. |
| **Shared-origin arcs** | One centre for the whole map, a long way outside it, and every label an arc about that centre. The labels then all bow the same way, by an amount depending only on where on the map they are — which is what a graticule does, and what makes an atlas page read as a piece of a globe rather than a flat sheet with words on it. It says nothing whatever about the shape of any individual country, which is either the point or the objection. Direction and distance are both controls. |
| **Spine — raw walk** | The interior-preferring walk, undoctored. Follows the country exactly and reads as a wobble. |
| **Spine — averaged & rounded** | The same walk, averaged and corner-cut. Better, and still following every accident of the walk. |
| **Spine — polynomial fit** | `x(s)` and `y(s)` fitted against distance along the walk. Degree and a fit-to-walk blend are both controls, the blend being how a curve smooth enough to write on can be kept honest about a neck it wants to cut across. |
| **Spine — circular arc through it** | **The default.** The walk finds the route; the whole of it is then reduced to a single arc. One curvature per label, so there is no ripple available to it at any zoom — which the cubic can still manage on a long awkward block — while the walk underneath keeps it going the way the country goes and through whatever neck the country goes through. The calmest of the eight that is still about the shape of the ground. |

Whichever is chosen, an algorithm returning nothing for an awkward shape is a normal event rather than an error, and the answer to it is a duller line rather than no name: the chosen baseline is tried first, then the parabola, then the straight axis.

*Which* serif is likewise a control rather than a decision, on the same panel with the ink. The choice is kept in `localStorage` so an afternoon of comparing does not restart at every reload, and is deliberately not read on the published map, where a stored preference would mean two readers seeing two different maps — there the first of each list ships. Changing either **re-fits** rather than restyles, since the font is what the widths were measured with and a new face is a new set of sizes. Three of the faces are web faces and are dev-only auditions: the stylesheet is fetched the first time one is picked and never otherwise, so nobody merely reading the map requests anything, and each falls back through the installed serifs so picking one offline gets the fallback rather than a blank map. The fetch is *waited for* rather than merely started, because a canvas measuring a font that has not arrived silently measures the fallback and every label comes out the wrong size.

The whole pass costs about 25 ms for the twenty labels on Borders, and it only ever runs when someone is looking: the button being switched on is what builds the group, and `paintRealm` rebuilds it only if it is visible. It has to be rebuilt on every repaint rather than kept, because a repaint is precisely the moment the answer to *who holds this subhex* changes, and a label placed against the old answer is sitting in the wrong country. The name groups live **outside** the layers they belong to: a realm layer is something you dim — Borders is most useful at half strength with the terrain showing through — and a name faded along with the wash it names is a name you cannot read, nor should lettering be inverted by a button meant for tracing scans.

The top of the map is then three kinds of thing, stacked in this order for three separate reasons. **Stronghold names** lowest: they name *places*, while a polity's name is a statement about a whole stretch of ground, so where the two collide the larger claim reads over the smaller — and a town's name is recoverable by hovering it, which a realm's lettering is not. **Realm names** above them, and above everything drawn, because a label a road can cross is no better than no label. **Stronghold markers** above both: a disc is a point rather than a piece of text, small enough that lettering over it hides the very thing it marks, and it is the thing you click.

Which means the stronghold names are a top-level group rather than a child of the marker layer — being a child fixed their height in the stack to the markers'. They are `linked` back to that layer in LAYERS, so its checkbox, its opacity slider and its invert button all still reach them, and the group is emptied and refilled on each render rather than rebuilt, since rebuilding the element silently drops the switch state, the opacity and the filter that row had set on it. That was a real bug while it was a child made afresh every time: renaming one stronghold brought every hidden name back with it.

The **Strongholds** row carries the same button, and it is the one that is **on** by default — a stronghold you cannot name is of limited use, where a realm name is a second reading of ground the map is already colouring. The markers and their names are one layer with two switches: a marker says a place is there and how big it is, the name says which place, and on a crowded stretch of coast it is the names that collide rather than the discs. The names are collected during the render and laid down in a group of their own **after** every marker, which is also a fix in its own right — drawn interleaved, as they were, a name reaching over its neighbour went *behind* that neighbour's disc and lost a letter or two.

Two paths that share an edge do not quite meet: each is rasterised on its own, each covers about half the pixels along the join, and half-coverage laid over half-coverage comes out at three quarters rather than whole — so a hairline of whatever is *behind* shows between them. The hex grid used to hide it, since it strokes every hex outline; with the grid off and the map zoomed out far enough for the hairlines to be dense, they read as a shimmer of a grid that isn't there. The geometry is not at fault: every one of the 24,834 shared corners on this map rounds to the same coordinate from both sides.

This was first fixed by having each patch bleed half a *screen* pixel past its own edge, which is right in principle and far too expensive in practice — a `non-scaling-stroke` is the one kind of paint that cannot be cached, since its outline is a function of the current transform, so twenty-five thousand hexagon edges were re-stroked on every frame of every pan and zoom. It is now done by putting the right colour **behind** the seam instead, which costs nothing per frame because it is only ever geometry: the basemap is built in layers laid wholly over one another rather than tiled edge to edge, and the terrain sits on that basemap, so where two of its colours meet the hairline shows the land or sea beneath rather than the page. Nothing is stroked. What is left is a faint line where two *different land* terrains meet and neither is Flatlands — a hills-and-mountains border against the green underneath.

Under every layer, and with no switch of its own, is a **basemap**: land and water and nothing else, in the same two colours the terrain palette uses for flat ground and open ocean. Water is at subhex resolution like everything else, so a bay bitten out of a shore hex is water here too. The land is a single **rectangle** over the whole grid rather than four thousand hexagons — under the water and the off-map filler it is never seen, and where it *is* seen it is one flat colour, so the hexagons were twenty-five thousand edges to rasterise per frame for a result one rect gives exactly. Water goes over it, then the off-map filler over that. The land is the **grid's own outline**, filled — every hex side with no hex behind it, stitched end to end into one closed loop of 547 points and traced once, since the grid's shape cannot change without `initGeom`. It traces the **real map** rather than the whole sheet grid — the padding columns are not part of anywhere, and were being drawn as a dark band down the right-hand edge that read as map which happened to be unlit. It has to be that shape rather than a rectangle: a staggered hex grid's edge is a sawtooth, the water drawn over it is hex-shaped, and any straight-edged backdrop shows as a step wherever the two disagree. It is also how the fill stays cheap — 4,230 hexagons is a quarter of a megabyte of path, rasterised every frame, for a shape whose boundary is 6.6 KB.

Two things make the tracing safe. The corners: adjacent hexes emit *identical* coordinates for the ones they share — all 24,834 agree — so stitching an endpoint is an equality test rather than a search for something near enough. And the way a side learns whether it is on the boundary: by asking its neighbours, not by asking the map what lies across it. `nearestHex` was the first attempt and is wrong at exactly the edge this is about — past the last column there is no hex, so it answers with the nearest one it can find, often in the row above, which reads as an interior side and leaves the chain in 238 pieces instead of one loop. It cannot be turned off because it is what the other layers are drawn *on* — with Terrain off you are reading what a scan or an isochrone says about the ground, and a shape without a shore beside it says nothing about where it is.

The **published sidebar is shorter than the local one**. Several rows exist because they are separate things to *draw*, not separate things to look at: terrain, the subhex fills and the drawn shoreline are one picture (the fills *are* terrain, at subhex resolution, and the line is where they meet), and the two grades of river are one river system at two widths. To a reader those are switches that reveal part of something and leave them wondering where the rest went; to whoever is drawing them they are exactly what needs separating. So on the published map Terrain drives all four coast/terrain groups, one **Rivers** row drives both grades, and one **Roads** row drives the roads and the trade routes, while locally they all keep their own rows. Only the sidebar changes — the groups keep their separate places in the z-order, which is why one row is handed the others rather than the groups being merged: the coast fills are split around the rivers, and neither that nor the river stacking survives being collapsed into one group. A group folded into another's row can keep its own weight through `op`, which is how the shoreline stays at the grid's 0.28 instead of being pulled up to full strength with the fills.

Two sorts of layer exist only when the map is served locally, and are **dropped from the list rather than hidden** — no row, no group in the SVG, nothing fetched. The tracing scans are one (`ref/*.png`, marked by having an `img`); the other is anything marked `dev`, which is scaffolding that answers a question about the *data* rather than about the world. **Sheet: river hexes** — the datasheet's own river flag painted per hex, for checking a drawn river against what the sheet claims — is one of those. The **Classic map** is exempt (`keep`): it is the map, not an aid to redrawing it.

Each drawn feature type has its own **Layers** toggle — Roads, Rivers (major), Rivers (minor), Trade routes, Coast fills, Coast lines, and Strongholds — with an opacity slider each, and locally an invert button (**◐**) as well. Invert is a CSS filter over that layer only, nothing in the data changes: it flips a dark reference scan into light lines, which is far easier to trace against, and it works on any layer, not just the images. **It ships only with the local build.** It is a tracing aid and nothing else, the scans it exists for are dropped from the published map, and a button left behind offering to solarise the finished map is a control whose only honest use has been taken away — so it goes out with them, and a published row is a checkbox, a slider, and whatever that layer has to say for itself. Three rows carry a second button (**A**) that switches their names: Strongholds, Borders and Warlords — see *Realm names, fitted to the ground* below. The reference layers sit right under Coast lines in the panel so they're next to what you're usually tracing, and they're drawn as true underlays — over the terrain, but beneath every feature you draw, so your own river always sits on top of the scanned one you traced it from. The **Coast lines** layer (the drawn black shoreline) is off by default, so you see just the filled land/sea subhexes; turn it on to see or edit the coast borders. **Hex IDs** (also off by default) prints every hex's number at its centre, so you can read ids off the map instead of hovering one hex at a time. It is **baked to images** the first time you switch it on: as live `<text>` it was 4,113 nodes each with a stroked outline, and text with `paint-order: stroke` is about the most expensive thing an SVG renderer can be asked for — every glyph outlined, stroked and filled again on every frame of every pan and zoom, which made the whole map stick. Nothing about the numbers ever changes, so they are drawn once to canvas and hung in the layer as four tiles: panning then costs four bitmap blits instead of four thousand outlined glyphs. Tiled 3×3 rather than drawn as one canvas, because a single canvas at this supersampling would be eighty megapixels and some browsers refuse canvases a fraction of that; tiling by the supersampling factor keeps each canvas at exactly the world's pixel size, which is the largest that can be relied on. Supersampled **3×**, so they stay crisp up to 3:1 and soften only past that. Every tile draws any label within a hex-width of its edge as well as those inside it: a number whose hex centre sits in one tile can reach into the next, and drawing it only from the tile that owns its centre left it sliced down the middle along every seam — 135 of them straddle one. The two tiles draw identical pixels and each clips to its own half, so the halves meet. They are held as blob URLs rather than data URLs — the same pixels, but a short string in the DOM instead of a megabyte of base64 per tile, revoked when the layer is rebuilt. The tiles are encoded one at a time, since nine nine-megapixel canvases alive at once is a third of a gigabyte. If no canvas can be had the old text nodes are still the fallback. A hidden layer is not a snap target: if you toggle a type off, new lines won't snap to that (invisible) geometry, though the hex grid still snaps and Alt still disables all snapping.

Coast fills sit directly on top of the terrain — they *are* terrain, just at subhex resolution — so the Layers panel lists them (and the coast lines) right under Terrain. The fills are split around the rivers in the draw order: land subhex fills, then the thematic ref scans, then the river layers, then sea subhex fills, then the **Classic map**, then the coast lines. The Classic map is deliberately above *both* halves of the coast fills, because it's the basemap you trace shorelines from and an opaque sea subhex painted over it hides the very coast you're following. The consequence is forced: since the sea fills sit above the rivers, a scan above the fills is also above the drawn rivers. Coast lines, roads, trade routes, the hex grid and strongholds all stay above it. A river drawn across a split hex therefore stays visible over the land half and slides under the open water rather than being painted over. Both halves share the single "Coast fills" toggle.

Origins are made and unmade from the map as well as from the panel. While the Isochrone panel is
open, **right-clicking a hex** offers a new origin there, moving the selected one to it, removing the
one already standing on it, and clearing them all — the entries adapt to what is actually under the
cursor, so there is no "remove" on bare ground and no "move here" on the hex the selected origin is
already on. They sit **above** the route entries rather than replacing them: which panel is open says
what you are most likely to want, not what you are allowed to want, and a route you were building
does not stop existing because you opened another panel.

Spread type and horizon belong to the origin as well. Selecting an origin loads its own Army,
Message, Rumour, or Relief mode and its own maximum-day limit into the controls; changing either edits
only that origin. Mixed origins still compete on arrival time, so a five-day courier spread can be
shown against a twelve-day army reach without either setting overwriting the other. Origin rows show
the saved spread and limit, and old saved origins migrate to Army with a seven-day horizon.

Large settled isochrones are raster-cached. A seven-day courier circle can cover almost every subhex;
keeping its thousands of SVG fragments and ownership masks live made the browser redraw all of that
geometry on every pan. The vector answer appears immediately, is painted once into a map-sized bitmap
when the browser is idle, and is then removed; origin rings remain live SVG controls above the cache.
Small reaches and unsupported canvases keep the vector fallback.

Dragging an origin stays synchronous and vector: every crossed subhex gets a real recalculation, with
no debounce, raster preview, or delayed catch-up. The drag fast path solves only the origin being
moved, reuses the other origins' fields, leaves the route drawing and route report alone, and does not
rebuild the isochrone rows or legend until drop. Hex centres, subhex counts, and subhex path strings are
cached because none of that geometry changes during a drag (the caches are cleared when adjacency is
rebuilt). On the 4,113-hex test map a seven-day Message update takes about 4–8 ms in this path; sending
the same pointer update through the full route/report repaint took roughly 470–490 ms. Drop still runs
the complete render and builds the settled raster cache described above.

## The route row, and two surfaces in one corner

**Double-clicking a route row opens its breakdown.** The step table is what a route is *for* — a route is a question and the table is the answer — and reaching it meant knowing the card had a switch of its own somewhere else.

It has to be recognised by hand, because the browser will never fire `dblclick` on these rows: a single click activates the route, activating recomputes, recomputing **re-renders the whole list**, and `dblclick` requires two clicks on the *same* element — the second always lands on a freshly built row. A row's own `ondblclick` is dead code, which is also why "double-click its name to rename" had never worked in all the time the sidebar advertised it. So the listener lives on the **container**, which survives re-rendering, identifies the row by **index** rather than by node, and is registered in the **capture** phase so it reads that index before the row's own click handler rebuilds everything underneath it.

The whole row answers, the name included, and **renaming moved to the row's ⋯ menu**. The name filled nearly all of the row, so reserving it would have meant that double-clicking "the row" mostly renamed instead — and between the two, the breakdown is plainly what a second click on a route wants. A menu the row already has is the better home for the rarer gesture.

**The swatch on a map button recolours its route**, raising the same palette the sidebar row's swatch does. Those buttons stack under **Layers** with a colour, a name and a time each, and read as a legend as much as a control — telling two marches apart by colour is the job they are doing, and with the panel shut they are the only thing on screen naming the routes. Each route is one panel, internally divided into its main action and an **eye**: no second bordered button or gap. The eye hides or restores that route's line, arrows and waypoint markers without deleting the plan or closing its readout. The timeline and every route panel read their width from the same CSS variable, so their edges always align. The dimmed legend row remembers visibility across reloads, and the toggle is one Ctrl+Z away from reversal. Hidden routes are excluded from the campaign timeline and from map context actions until shown again. The swatch click is stopped so it does not also reach the main action; both swatches and the drawn line repaint live as the picker is dragged.

The readout also **steps out of Find's way**. Both defaulted to the bottom-right, so the breakdown opened straight over the search box. That is the same collision that had already been settled once — the layer list and the readout both opened top-right and looked like one broken panel, so the readout took the bottom — arriving again one seat along now that Find has moved into the bottom corner. Rather than hand out fixed corners and wait for a fourth surface, the readout now asks where Find is and places itself beside it, or above it if there is no room. It yields rather than Find because Find is the smaller surface, the one you keep open while working, and the one just put in that corner deliberately. A position you have dragged it to is never second-guessed.

## Orders, halts, and the best order to visit them in

A route is now billed the way orders are actually written: **in whole days, one order per halt**. A run of 3.2 days is a four-day order and the remaining 0.8 is spent whether it was needed or not. That whole-day figure is what the card, the route rows, the map buttons and the hover preview all report, with the exact distance marched kept beside it — because the gap between the two *is* the waste, and the waste is the thing a plan can actually do something about. The card names it outright: `12 whole days over 4 halts — 1.3 d wasted`.

**Whether the column halts is a switch, at two grains.** *Stop at waypoints* supplies the route-wide default, while a waypoint's right-click menu can explicitly make it *Pass*, *Visit*, or *Wait* for a chosen number of whole IRL days. Pass still sends the column through the place without ending its current order; Visit ends and rounds the order there; Wait does the same and then adds its stated delay. Explicit Visit and Wait override a route whose unmarked waypoints normally pass through. Pass markers are drawn smaller and thinner — a lesser thing than a stop, said by being less of a marker rather than by a new symbol to learn. Setting out is never a halt unless it carries an explicit Wait, and arriving always is.

Both live in a **March** group between Column and Conditions, with the *Optimise order* button on the same line as the switch — the switch is the assumption the search is made under, so reading it and pressing the button is one gesture. That group travels between the Routes and Isochrone panels with the other two, and hides itself on the Isochrone panel, which has an origin and a horizon rather than a list of places to be at, and so has nothing to halt at and nothing to reorder. A route saved before the switch existed has no opinion about it and is read as halting: taking silence for "off" would quietly rebill marches that were planned with stops in them.

**Optimise order** searches for the arrangement of waypoints that costs the fewest ordered days, and asks which ends to hold as it does: keep the start, or keep both ends. Which of the two you want is a fact about the march in front of you — a column ordered to end up somewhere is a different question from one merely told where to call — so it is asked at the moment of asking rather than kept as a setting to be remembered. A march that comes home is drawn by putting the starting hex down again as the last waypoint and holding both ends.

It sorts on **orders, not exact days**, which is the whole point. Two arrangements marching 11.4 and 11.9 days cost the same twelve days if they halt in the same places, and an arrangement that marches *further* can cost a day less by landing its halts more tidily; sorting on the exact total would return the wrong answer with great precision.

The search is Held-Karp over subsets, and exact — a dozen waypoints is 4,096 subsets, and measured at 12 waypoints the whole thing takes about four-tenths of a second, at 15 about eight-tenths, which is where the limit is set. What makes it more than a plain travelling-salesman problem is two things. The column carries **state** between legs — afloat, ashore with ships, ashore without — so the cheapest way to leave a stop depends on how it arrived, exactly as `routeLeg` already has to handle. And the rounding is **not additive**: a run through pass-through waypoints is rounded once at its end, so a partial answer is a *pair* — orders already spent, and the fraction still running — and neither number alone says which of two partial answers is worth keeping. Both are kept, as a small Pareto frontier per subset. With every waypoint a halt the frontier is one entry deep and it reduces to the ordinary DP.

The cost matrix comes from one Dijkstra field per waypoint per departure state, built **on demand**, so a state no arrangement can actually leave in is never searched from — which on an inland march means one field per waypoint rather than three. Checked against brute force over every permutation for four- and five-waypoint routes in all three modes, on scrambled orders and with a pass-through in the mix: same answer every time, and the figure the search reports is the figure the route reports once the new order is applied. A route the search cannot join up at all — a waypoint across water with no ships — is left alone and says so.

One honest limit: the *path* between two waypoints is still solved for the fewest exact days and then billed in orders. Minimising the exact cost of a run also minimises its rounding, so the two agree wherever a run is a single leg; where a run crosses pass-through waypoints the solver's state trade-offs are made on the exact total, and could in principle differ by a fraction of a day from what the ordered billing would have chosen. The reordering above is exact in orders; the pathfinding under it is exact in days.

## The next click, before you make it

In Route mode the hover readout ends with **when the active route would arrive** at the hex under the cursor: `arrives in 38 IRL days (+18 d)` — the whole march from its first waypoint, with what this stop would add in brackets after it. One line and one unit, in the same whole-day orders the card reports, so the preview and the card cannot quietly disagree the moment you click. A hex the column could reach inside the day it is already marching therefore adds nothing at all, which is the truth about it and half the reason the figure is worth having before the click. The in-game figure is left to the card, since the question a hovered hex asks is how much further, not what the date would be. It answers the question in the order it is actually asked: you are hunting for the hex the column can reach in four days, not checking one you have already committed to. It is the exact figure the route will report once the waypoint is placed, not an estimate — hovering a hex and then clicking it gives the same number to the last decimal, because both come from the same solver over the same states.

The work is one Dijkstra field out of the route's **last stop**, which is precisely what solving one leg costs — `dijkstraLeg` builds the same field and then reads a single hex out of it. So the whole map is answered for the price of one more leg, and every hover after that is a map lookup. The field is built on the **first hover after the route changes** rather than eagerly, so a route nobody is measuring costs nothing, and it is thrown away by anything that recomputes the route: a waypoint placed or dragged, a settings box, an undo, a road drawn under it.

Up to three fields, not one: the column can be standing at that last stop afloat, ashore with ships, or ashore without them, and which of those is cheapest to *leave* from is not settled until the destination is known — securing a fleet is dear and having one is cheap. Taking the minimum over all of them at lookup time is the same joint optimisation `routeLeg` already does across a route's legs, which is why the preview and the placed waypoint cannot disagree. A leg that starts from a waypoint marked **forced** is previewed at the forced pace, since that is the pace it would be solved at.

It is silent where it would be misleading: over the last waypoint itself, while the Isochrone panel is open or **Set origin** is armed (a click there moves an origin, not a march), and when the route *so far* is already broken — the panel names the pair of hexes that defeated it, and the readout does not blame every hex on the map for it. A hex the column simply cannot get to says so, which is a useful answer: a shore with no ships, a crossing the weather has shut.

## Waypoints are dragged

A stop is moved by dragging its marker, and the march re-solves live for each subhex the marker is held over, before it is dropped. Isochrone origins use the same gesture and repaint their reach live while held. Before, the only removal was the *last* waypoint, so changing one in the middle of a route meant taking the whole tail off behind it and rebuilding — while the thing you could see and point at was the one thing that would not move.

An interior waypoint on a stronghold constrains the route to that subhex without pulling the drawn
line over to the stronghold marker. Its ring stays on the keep so it remains the thing you selected
and drag, while the incoming and outgoing road, river, or ordinary march geometry carries on
naturally. Only the route's actual start and destination are drawn to a stronghold gate. This avoids
the small out-and-back loop made when a through-route passed a keep near the side of its hex.

Three details, each of which had to be got right for it to feel like moving a thing rather than operating a control. The marker follows the pointer directly and the hex under it is **outlined**, because a marker that jumped from node to node would hide which hex it was about to land on. It carries its **subhex**, unlike a counter, so dropping a stop on the far bank of a river means the far bank. And the route re-solves **on drop, not continuously**: each solve is a fresh pathfind over the whole march, and following the pointer with it would compute a dozen answers a second that nobody asked for.

A press that does not move is **inert** — deliberately not treated as a click, since a click on bare map plants a waypoint and a press on a marker that turns out not to have moved should not plant a second stop on the one already there.

It also needed the **hover layer to stop taking pointer events**, which is a bug the dragging merely exposed. That layer exists to show you what you are pointing *at*, so anything in it that intercepts the pointer is answering a question with a lie — and it was: the highlight for a split hex is a **filled** region polygon, unlike the stroke-only outline a whole hex gets, and a filled path is hit-testable. It sits above the route layer, so a waypoint on one bank of a river could not be grabbed at all — the press landed on the highlight drawn to point out the very marker you were reaching for. Dragging worked everywhere else, which is what made it look like a subhex problem rather than a stacking one. The rule is now set on the group, since "nothing in here is a target" holds for the whole layer and stating it once means the next thing drawn into it cannot forget.

Making it work needed one change to the drawing order: the marked line is now drawn *first* and the stop markers over it. It was the other way round, which looked almost the same — the line crossing a hollow ring rather than stopping at it — and made the markers **ungrabbable**, because the line passes through every waypoint it visits, so at exactly the point you aim at to pick a stop up, the line was topmost and took the press. The line is also `pointer-events: none` now: it is a drawn answer, not a control, and has no business intercepting anything.

## A march you can read off the map

A long route was the hardest thing here to look at, and neither reason had anything to do with the solving.

The first is that **a column coming back the way it went was drawn on top of itself**. Both passes trace the same road geometry, so the second was laid over the first pixel for pixel and simply disappeared: a march out to Kisra and home again looked exactly like a march to Kisra, and the twelve days it billed for looked like six days' worth of line. Every stretch walked more than once now gets **a lane per pass**, so a doubled road reads as two lines running together — which is what it is. Which lane a pass gets is the order it walks the stretch in rather than its direction of travel, so on an out-and-back the outward leg keeps one side of the road for its whole length and the return keeps the other, instead of the two swapping sides at every bend. **A route that never crosses its own path is drawn exactly where it always was**, still sitting on the road it follows: the geometry is handed straight back untouched rather than rebuilt identically, since any nudge at all would be a lie about where the column walked.

A stretch walked more than once has to spread its passes across it, and there are two questions: how wide, and in what order. The order is the one that took three goes.

It was first a signed offset from a canonical ordering of the segment's two endpoints, which is a fact about the hex ids and not about the march: which side the outward leg took was arbitrary and could differ from one segment to the next, and every time it changed its mind the tracks crossed. Then it was **keep left** — measured off the walker, so an out-and-back straddles the road on its own, left of east being north and left of west south. That is right for two passes going opposite ways and wrong for two going the *same* way, which it stacked one outside the other on the same side of the road: two tracks running alongside each other with the road bare beside them, and, where they finally parted, the one heading south obliged to cross the one heading north to get there.

So the passes are now **ordered by where they are going**. A pass is a run of doubled segments walked without turning round; every pass over a stretch belongs to a corridor — every doubled segment reachable from another either by lying next to it along the march or by being the same ground walked again — and each pass leans to one side or the other by the road it came in on and the road it leaves by, measured against the corridor's own frame. Sorted by that lean and laid out in order, the pass that peels off south runs on the south side of the stretch before it peels, which is the whole point of separating them and is also exactly what stops them crossing where they part.

For an out-and-back this reduces to what keeping left already did: the outward and return lean by their approach and their departure, which are at opposite ends of the corridor, and the hairpin at the far end joins the two lanes it finds. Lanes are two marker radii apart, so a pair sits at ±R and the half-turn between them comes out at exactly the marker's radius. The spread is capped at three radii either way.

Where the roads at a junction lie on *opposite* sides of the corridor there is a right answer and the ordering finds it. Where they lie on the same side there is none: one track has to get across the other, and all the choice buys is which — and the choice goes to the end where the passes actually part company, since that is the one anybody is reading.

The lanes sit **one stop-marker's radius** out, and that number is not an aesthetic choice either: it is what makes the turn work. Where the column reverses, the two lanes have to be joined, and joining them with a straight run across gives a square fold a lane wide — a notch, which is not what a road doing a hairpin looks like. So the turn is drawn as **an arc about the vertex the line turned at**, and that arc is tangent to both lanes for free: a lane's offset is perpendicular to its direction of travel, so a radius from the vertex out to the lane meets it at a right angle, and any circle centred there leaves and rejoins running exactly the way the line was already going. Nothing is fitted; the turn's radius is simply how far out the lane is. Put the lanes at the marker's radius and the hairpin at a stop becomes a circle of the ring's radius about the ring's centre — **the loop and the marker are the same circle**. The turn does not sit near the stop or inside it; it *is* the stop, traced by the line that made it.

Which way round it wraps is then not a separate question. Given which side each track is on, the only sweep that leaves and rejoins them running the right way is the one carrying on **past** the turn before coming back; the other would cut across the approach and cross the very lines it is joining. Tangency and not crossing are the same condition, and exactly one arc satisfies it — so the wrap direction is settled by the corridor's vote, one junction away, rather than by anything at the turn itself.

The arc is for the column **turning round**, and only for that. It used to fire wherever the two ends of a join happened to be equidistant from the corner — which on an ordinary bend they always are — and the result was a little hoop sprouting at any corner two tracks passed each other on, reading as a waypoint that was not there. Ordinary bends are mitred instead, which keeps a bend a bend rather than opening a notch a lane wide, held to within twice the lane width of the corner since the crossing runs away to nothing as a bend tightens and a spike most of a hex off the road is worse than a slightly cut corner.

Further passes **build up outward**. Two passes going opposite ways straddle the road at one marker radius each; passes going the *same* way cannot share a side, so they stack — the first at one radius, the second at two. A pass, once placed, stays: a third and fourth crossing wrap around the outside instead of shuffling everything inward to make room, so the line the first two drew does not move when a later one turns up. Capped at three rings, six passes over one stretch being past telling apart anyway.

Then every bend gets **rounded**. A solved route is a polyline through node points, road ends and edge touch-downs, and a polyline turns corners; on a march following a coast or a river through a dozen hexes those corners come thick and fast, and drawn sharp they read as a jagged thing rather than a road — the mitre is geometrically right and the eye reads it as damage. So each bend is given a fillet, a circular arc tangent to both sides that cuts the corner off.

Two limits matter more than the radius. A fillet may take **no more than a shade under half of either segment it sits between**, so two fillets on a short segment cannot eat into each other and a corner between two two-unit hops is left alone rather than rounded into mush. And it may not carry the line **more than an eighth of a hex off its own corner**, whatever the radius asks for, because that corner is often a touch-down planted on the edge between two hexes precisely to keep the line inside them, and rounding it too generously undoes the tidying that put it there. Both clamps work by shortening the tangent and re-deriving the radius from it, so the arc stays tangent whichever of them bites; over eight thousand random polylines the worst drift measured was 2.6 units against a cap of 6, and the two ends never moved at all.

The rounding runs over the *drawn* line rather than the solved one — after the lanes and their tapers — so a route that never doubles back is rounded too, and so are the joins the lanes introduce. The hairpins come through untouched: they are already arcs, and an arc's own sampling turns through fifteen degrees at a time, which is below the angle worth filleting.

A lane change used to happen **at a point**. The offset was a per-segment constant, so where the count of passes changed the line stepped sideways in no distance at all and left a hard zigzag exactly where two tracks were meant to be separating — and at a shallow crossing the step went the wrong way for the eye, bringing the tracks *together* for its length before they parted. The offset is now a function of distance along the line rather than of which segment you happen to be on, and it eases across on a smoothstep centred on the vertex, over about half a hex where there is half a hex to be had. A taper stops short at a reversal or at the next lane change, since easing on through either would be easing towards a lane the line never reaches.

### A road does not stop at the hex boundary

It runs on to its own mid-hex point, and on a hex split by a major river that point can be **on the far bank**. The drawn line followed it there, which put the column across the water a step early, and the crossing that came next then had to bring it back: an out-and-back over the bridge some twenty units long. Under a three-unit round-jointed stroke that is invisible — except that it is long enough to turn an arrowhead round, and a march heading north-east showed one head at the bridge pointing south-west. A run's tail is now cut back to the region the step it belongs to actually arrives in; only the tail, and only inside that step's own hex, since the head of the run is in the hex it came from and is none of this step's business.

The arrowheads were made less brittle at the same time. Which way a head points is taken from **the chord across its own length** rather than from the one facet of the polyline it happens to be standing on — a facet can be two units long where the drawn geometry is fine, and reading direction off it asks the question at a scale far below the one the answer is drawn at. It also lines the heads up along a curve rather than along whichever facet they landed on.

### A river drawn along a boundary

Rivers here are very often drawn *on* the edge between two hexes rather than through the middle of one, which is what a river between two counties looks like. Two things went wrong with that, and both of them said a fleet could sail where it plainly could not.

The first is a **graze**. A river following a boundary belongs to whichever side of it the drawn line happens to fall, and near a corner it strays across for a few units and back. Four units of stray river was enough to make the hex it grazed a river hex — navigable, boardable, and joined by a sail link to the hex the river really runs down. Gerénéi picked up a channel that way, one running past the far side of its own boundary. A hex now needs the river to be *in* it, about half a hex of it, before it counts: seven hexes across the map lost a river they only touched, and none gained one.

The second is the **alternation**. Sampled every four units and asked which hex each sample is in, a boundary river can answer A, B, A, B all the way down. Read run by run that came out as a long series of A→B links — and a link here means a fleet can sail from A to B. So the one thing such a river plainly does not offer, a passage from one of its banks to the other, was the only thing it offered. Three or more runs flip-flopping between the same two neighbours are now read as one **reach** with a hex on either side of it, and reaches are what get joined: every hex bordering one reach to every neighbouring hex bordering the next. Two hexes facing each other across the same reach are not joined at all — they are the same water, and getting between them is a bridge or a ford, which is a different question with its own answer. A river that genuinely crosses an edge makes one run in each hex and no alternation, so it comes through untouched.

Between them these dropped 31 sail links from the map and added 8. No waterway was cut in two: the river network had 26 separate navigable systems before and has 26 after, each just short of the hexes it was only grazing.

The threshold is a quarter of a hex, which is a number with two jobs and had to be tuned against both. Too low and Gerénôi keeps the six units of somebody else's river that strayed over its boundary; too high and the Ayauda loses its way down to the sea, because that river runs along a chain of hex edges and its runs through 1937 and 2027 are only eleven units each — brief, and load-bearing.

The same boundary is what made a port of a keep with no water in its hex. A stronghold counted as a port if it stood on, **or bordered**, navigable water — and a river drawn along an edge is recorded on one side of it, so the hex on the other side borders that water without having any. Gerénéi was securing a fleet on those terms: seven days of shipwrighting at a keep whose own hex is dry, and then a launch straight into the channel running past the far side of its boundary. The inference now stops at the hex line — the water has to be in the stronghold's own hex, its own subhex being a river bank or another subhex of the same hex being sea or river — and that is where the fix belongs. Launching straight into a neighbouring hex's water is allowed again: it is the one place a fleet may enter water it could not have sailed to, and it is meant, since a port is a place where boats are put in and which hex the drawn river fell in is not a fact about the harbour. Taking *that* out was the wrong cut — it also cost the Ayauda its way to the sea — and with the port test tightened the keep that was reaching across is not a port at all and never gets there. An explicit flag still overrides either way. Thirteen markers of eighty-four stop being ports by this; the ones that keep it are the ones with water in front of them, which a coast hex has by construction, since it is split into land and sea subhexes.

### Sailing a boundary reach

The subhex machinery keeps a marching column from walking over water that lies between two hexes' banks: where a major river crosses an edge both hexes have a bank on either side of it, all four regions touch the edge, and pairing them blindly would march the column across the channel. That test is right for marching and asks the wrong question of a fleet — and where the drawn river runs **along** the shared edge it gives the wrong answer to every pair, ruling all four banks out as separated by the water when the water is precisely what the fleet is on.

So a boundary reach carried nothing. The Ayauda's own channel could not be sailed from one hex to the next, and the search paid a day to go ashore at Akanin and launch again on the far side — which is not a thing anybody does to get down a river they are already on, and it drew the line off the water and back. The test is now waived for sailing on such an edge; being navigable, being on the edge, and the drawn river actually running between the two are all still required. Down the Ayauda to the sea went from 1.60 IRL days with a disembark and a re-embark to 0.70 with neither, and the march the readout was showing — 1938 straight to 1937, which the river does not do — now goes the way the river goes, through 2028 and 2027.

This had been true since long before any of the work above; checking the same route against every commit back a week gives the same wrong answer.

And a river drawn along a boundary is **both** hexes' river. Only the hexes the drawn line physically fell inside counted as being on it, which is a fact about which side of the boundary the hand that drew it wandered to — so Gerénôi, standing on the west bank of the reach that runs down its own eastern edge, was not on a river at all: no bank, no harbour, nowhere to put a boat. Every hex sharing an edge the river runs along is now on that river, either bank can embark, and the two are the same water. Fifteen hexes gained a river they were always beside, and three strongholds a harbour.

### A step that does not move the column

Going ashore, taking ship, spending the month securing one: these change the column's *state* and move it not an inch, so they have nothing to contribute to the drawn line — they happen where the line already is. Drawing them anyway meant drawing to the subhex's own centre, and on a river bank that centre is nowhere near the water. Coming off the sea at Akanin to launch again into the next reach, the line left the river, struck out twenty-two units across dry country to the middle of the bank, and came back.

They are skipped now. And where a step *is* taken afloat but has no drawn river to trace — launching from a port into the next hex's channel, which is a move the river-mouth rule does not have to allow — the line aims at the nearest water in the destination subhex rather than at the bank's midpoint. It is the same idea as anchoring a stop on its stronghold marker: draw to the thing the step is actually about. What is left is one straight hop between two reaches with land between them, which is the honest picture of what that move is.

### The lanes stop at the water

A lane is a cosmetic displacement, and it is not allowed to make a claim about the ground. Six units is nothing on a fifty-unit hex until the line is beside a river, and then it is the difference between one bank and the other: an out-and-back that forded twice was **drawn fording four times**, its two tracks stepping over the water and back again purely to get out of each other's way. Nor is it only the lane — the half-turn at a hairpin is a whole lane's radius wide and a fillet takes its own bite of the corner, so keeping the water clear needs room on both counts.

So no lane is taken within two lanes' width of major water, and no corner is rounded across it. The tracks close up as they come to the river, cross it together on the one line the column actually took, and part again on the far side, which the tapers do for free once the offset is zero. It costs nothing where it applies: the stretch that gives up its lane is a ford, which is one place on the map that could not be mistaken for anywhere else. Over 166 out-and-back marches between river hexes, the number that drew a crossing the march never made fell from 37 to 3, and the phantom crossings from 82 to 6, with **none made worse**. `throughSharedEdges` refuses the same liberty for the same reason, and the cosmetic shortcut that skips the node in a hex the column only passes through now refuses it too — cutting that corner where the two halves of a hex are split by a major river drew a march that forded once as fording three times.

### A pretzel at a bridge

Where a route recrosses itself at a river crossing, all of the above met a case none of it was written for, and the result was a knot: a small closed loop with no waypoint behind it, and a hard sideways step of most of a hex beside it. Three things had to be true at once, and all three are true at a bridge.

The geometry there is **fine**. A crossing is traced through drawn road and river points three or four units apart, where the rest of a march is drawn in strides of thirty. The crossing is walked **more than twice** — over, back, and over again — so one stretch is two lanes out while what abuts it is one lane out or on the road itself. And those changes of lane fall **at the turns**, because turning round is what a route does at a crossing it is using twice.

The taper was suppressed at every reversal, on the reasoning that a lane never changes at one: the offset is measured off the walker, so both passes of an ordinary hairpin are the same distance to their own left and there is nothing to ease. True of an ordinary hairpin, and false here — so the line jumped eighteen units in no distance. Worse, having jumped, the two ends of the join now stood at *different* distances from the corner, which disqualified them from the arc as well, so the turn was drawn as a bare step. And at the joins either side, ends that should have been half a circle apart were half a *unit* apart, on the same side; the tangent condition then chose between "no turn at all" and "all the way round" and took the second, drawing a full 360° circle of the lane's own radius.

Three fixes, each narrowing a rule that was too broad. A taper is now suppressed only where the lane genuinely does not change, rather than at every reversal — which fixes the step and, because the two ends then meet the eased value from either side at equal distances, restores the arc at whatever radius the ease has reached. The arc additionally requires its two ends to be on genuinely **opposite** sides of the corner. And `turnArc` refuses outright to sweep more than half a circle, since nothing here ever wants more: a fillet turns by less than a straight-about and a hairpin by exactly one, so a sweep past that is proof the ends are not what they were taken for.

The second is that a line has no direction. Which end a march started from was readable only by finding the waypoint list and counting, and on a route that loops it was not readable at all. So the line is now **solid and carries arrowheads along it**, spaced by drawn length rather than by ground — what makes a route unreadable is how long the line is, and a per-hex spacing would put an arrow into every step of a mountain crawl and two into a trade hop spanning six hexes. A march too short to hold a full interval still gets one, at its middle. Anything that would land on a stop is dropped: an arrowhead fills in a hollow ring and turns a stop into a blob, the ring is the more important mark, and the arrows either side of it say the same thing about direction.

The heads are drawn **big** — six strokes long and nearly five wide, wider than the lanes are apart. A head sized to sit politely on the line is a head you have to go looking for, and the point of it is to be answerable at a glance and at a zoom where the line itself is a thread. The size then sets the spacing rather than the other way round: at the interval that suited a small head, a big one turns the line into an unbroken chain of chevrons, and on a doubled stretch the two lanes' heads interlock into a braid with no plain line left anywhere to tell them apart. About a hex and a quarter apart leaves every head clear line either side of it.

The dashes are gone with the arrows' arrival. They were doing a job — *this is a plan, not a drawn feature* — but the colour already says that, since roads are orange and a route wears its own swatch, and a dashed line broken again by arrowheads is two kinds of interruption arguing with each other. Solid, with arrows, says both things at once: one continuous march, going that way.

### Faint means "not the one being talked about"

An inactive route is drawn thinner and half transparent, which says *this is not the march under discussion* — and that only means something while something on screen is doing the discussing. Two things can be: the **Routes panel**, which names the active route in its heading, its settings and its list, and the **readout card** on the map, which is that route's answer. With both away, the active route is a fact about the state and about nothing the reader can see, so dimming the rest dims them in favour of a distinction nobody is being shown. What is left is a map with one march legible and the others half there for no stated reason. When nothing is singling one out, they are all drawn as the one.

It is asked as a question of those two rather than kept as a flag, because a flag would be a third thing to remember to update. Opening or closing the panel, switching to another panel, and dismissing or recalling the card all repaint — which re-solves, and sounds heavy for a change of opacity, but it is the same work a dragged waypoint does on every frame, and the repaint is told not to touch storage or recompute the isochrones, which have no opinion about any of this.

## A route's colour is its own

Routes used to be handed out of the one shared palette above, and the trouble with that is what that palette **is**: the colours the map paints the ground in. Switch the Warlords or Borders layer on and a route in one of them is a line laid over an acre of itself — Legion VII's green march across Legion VII's green province is not a march anyone can follow — and the five neutral spares ran out after five. Worse, a route that set out from a hex a counter was standing on **took that counter's colour automatically**. That was a nice idea, the V's road drawn in V's colour without anyone choosing it, and it was the single most reliable way to produce a march that vanished the moment the layer it matched came on. It is gone, and so is the sharing.

Routes now have ten colours of their own, chosen for one job: being a line, over this map, that nothing else on it is. Each is kept clear of the terrain beneath — mid-green Flatlands, tan Hills, grey-brown Mountains, the three blues of Ocean, Sea and Lake — of the drawn features it will be running along, orange roads and blue rivers, and of all seventeen realm washes: nothing within about ten of any of them by ΔE2000, and nothing within fourteen of anything else in the list. They are brighter and more saturated than all of it, which is the point. The map's own colours are washes and fills, meant to be looked past; a route is a line drawn on top and meant to be looked at.

**Orange leads**, because that is what a march is — the warmest, most forward colour on the wheel that this map does not already use for a *fill*, and the first route anyone draws should be the one that shouts. It is a hotter orange than the roads' burnt one, which is the single real compromise in the set: the two are within about eleven, and it is bearable only because they are told apart by weight and shape rather than by hue. A road is a thin quiet line; a route is thicker, solid, and carries arrowheads.

The order after it deliberately does not walk the rainbow. Consecutive routes want to be as **unlike** each other as possible, since routes one and two are the two that will be on screen together, so the list jumps across the wheel each time — orange, ice, pink, green, violet — and only settles once there are more marches on the map than anyone reads at once. Paper and charcoal come last: they are the two answers to ground too dark or too pale for a hue, and want choosing rather than handing out.

A browser that already has routes in it is wearing the old colours, and for most of those routes that is a legion's — which is the fault, sitting on screen, that changing the palette was meant to fix. So they are moved across at the next load. Only the **fifteen realm colours** are touched: the old spares were chosen to stay clear of the map in the first place, two of them survive into the new list unchanged, and a route in one of them reads perfectly well, so moving it would be changing a right answer for the sake of tidiness. Anything mixed by hand in the custom picker is left alone too — it was chosen, and a choice outranks a default. The pass is quiet rather than an undo step: it runs before the map is on screen, against a state nobody has seen, so there is no *before* for a Ctrl+Z to return to, and one that put a march back into Legion VII's green would be undoing the fix rather than an edit.

## The isochrone speaks in subhexes

Everywhere else on the map, a hex a coastline or a major river has cut in two is *two places* that
happen to share an outline, and the pathfinder has treated them that way for a long time. The
isochrone used to collapse them again on the way out — one figure per hex, taking the best of
whatever reached it — so a port whose bay a fleet could sail into came back shaded over its whole
hex, land included, even for an army with no ships and no way ashore. The reach was right; the
reporting threw the distinction away.

So every field the isochrone builds is now keyed by **hex and region together**, in all four modes,
and every band it paints is the region's own shape rather than the hexagon around it. A coastal hex
can be half shaded and half bare, which is the truth about it; the tooltip answers for the subhex
under the cursor and says nothing over the half that is out of reach. Hexes nothing has split have
exactly one region and read exactly as they always did. Word of a siege is given to every region of
a hex alike — news does not slow down at a shoreline — so it is the march that does the dividing.

**Without ships, nothing at sea is shaded at all.** With "Start as fleet" off, the isochrone drops
every sea subhex from the field — a fleetless column has no billet on the water, so painting it as
ground held was never right. Only the field is filtered, not the search: an army allowed to secure a
fleet can still spend its month doing so and cross a strait, and the land it reaches on the far side
shades normally. A strait drawn as a gap between two shaded shores is the honest picture of
that. River subhexes stay either way, since a bank is walkable ground that happens to be sailable
too. One consequence worth knowing: a siege origin placed on a *sea* subhex with no fleet gives an
empty field, because nothing can reach it inside any budget shorter than the securing month.

**Whether a subhex reaches a hex edge** is decided by sampling that edge — and the sampling used to
lie. Each sample was nudged 0.18 of the way to the hex centre before being tested, which on a 29px
edge is four and a half pixels: not a test of the boundary at all, but of a line well inside the hex,
and a coastline crossing at an angle has moved a long way by then. Only five samples were taken, and
those bunched between 12% and 88%, so a region reaching the edge near a corner was missed outright.
Two bays that plainly met along 40% of their shared edge came back as not touching, and a fleet in
one had to put ashore and launch again — a whole wasted day — to reach water it was already looking
at. An edge is now read exactly as the land-meeting table reads one: 32 samples across its full
length, `regionAtEdge`'s own small inset, and the same 3-sample threshold, because one sample is an
artifact and a run of them is a shore. Across the whole map that reconnects 278 region pairs and
disconnects 105 — and the disconnected ones hold 0–6% of their edge, several of them literally none,
which is to say they were never touching and the deep probe had been reporting a neighbour it found
inside the hex. Memoised per hex, region and neighbour, so the extra samples cost nothing after the
first pass; `deriveAdj` clears the cache when the ground changes shape.

The area outlines are drawn the way the region selection is: the whole shape is stroked and then
masked by everything inside it, which hides the inner half of every line and, with it, every line
between two pieces the same area holds. What survives is the silhouette, holes and coastlines
included, without computing a union of several hundred polygons. The origin-list count stays in
whole hexes — a hex cut in two is still one place on the map, and counting it twice would flatter
whoever happened to hold a shore.

## The relief army

The Isochrone panel's fourth spread, **Relief army**, turns the usual question inside out. An
ordinary isochrone asks how far a force can get; this one asks what a defender actually needs to know:
*how far away can I station this force and still have it arrive in time*. The origin is wherever it is
happening — a siege, a battle, a landing — and every shaded hex is somewhere you could quarter troops,
shaded by how many days they would take to get there: news travelling out to them as the crow flies
(rumour, 90 mi a day, or a courier at 240), and then the column marching in over the roads.

Each leg is billed in **whole days, and separately**, then added. Orders are issued in whole days,
and these are two orders rather than one — the news lands during a day and the column sets out on
the next — so a rumour that takes three hours and a march that takes six still cost two days between
them, and no hex but the origin's own can come in under two. The default budget is **4 days**;
hovering a hex breaks the total back out into its two legs, with the unrounded figures in brackets,
because which leg is eating the budget is what you can do something about. A hex held back by the
march wants a road; one held back by the news wants a courier posted, not a garrison moved.

The march is costed **inward**, in the direction it is actually made, which is not the same
calculation as the outward one every other mode does. A hex is paid for by the step that enters it,
so a march solved outward from the origin never pays for the hex it is aimed at — and on a fortress
in the mountains that is a whole day at half pace, unpaid, on precisely the ground fortresses stand on. So
this mode runs the movement graph backwards, recovering each node's incoming moves from its possible
predecessors and expanding each hex at most once, which keeps the work in proportion to the area
covered rather than to the map.

Several origins are several emergencies, and a hex goes to whichever one it can reach soonest; the tooltip
names the other and says how much later it would arrive, since a hex that covers two sieges is
usually the hex you want. How long you really have is a judgement the map cannot make for you — but
the walls falling is not the end of it, since taking a stronghold in hand costs the besieger 5
in-game days for a fortress (1 IRL day), 1d6 × 5 for a town (1–6) and 2d6 × 5 for a city (2–12).
The panel's "How long you actually have" note keeps that table within reach of the box.

## Movement semantics

- Route lines visually trace the drawn feature they use: a road step follows the road's drawn path, and a sailing step follows a drawn river's path where one connects the two hexes. Open-sea and ordinary off-road steps go centre-to-centre; where that chord would cut across a lake, bay, or other concave water boundary, an off-road step stays in its solved land subhex and bends around the shore.
- Road between two hexes (drawn line passing from one to the other) → road speed; crossing a river on a road = bridge.
- Roads are a **connected network**, not just per-hex adjacency: an army keeps road speed only while following one continuous road. Where the drawn line goes matters — two roads that merely pass through the same hex are treated as separate unless their lines actually **touch or cross** inside that hex (a junction), so you can't cut a corner or hop between parallel roads for free. An army can always leave a road and march off-road between adjacent hexes at the slower off-road rate (it just loses the road bonus), and re-join any road at the hex where it arrives.
- Ferry is **not drawn** — there is no ferry tool. A ferry is simply what a road does where it crosses a major river, which nobody can ford: the step is free for the whole column, wagons included, and the breakdown labels it `road, ferry` (a road over a *minor* river is a `bridge`). Draw the road across the river and the ferry is there.
- Major river (3 px): no fording at all — you need a road across it (bridge/ferry); navigable by fleets. A fleet already at sea sails straight into and along a connected major river with no stronghold or embark (it's continuous water). Boarding ships from land still needs a coastal/large-river port.
- Minor river (1 px): fordable by all incl. wagons; delay = ½ day per mile of column (cavalry free).
- Contradictory overlaps are prevented: a new river drawn on top of an existing river (either type) is rejected — erase the old one first. A road drawn over a river is fine (that's a bridge). When stacked lines are erased, the most recently drawn one goes first.
- Trade route: bulk shipping = road-grade infrastructure; armies traverse it end-to-end at road speed — all at once or not at all, no stops partway, endpoints need not be strongholds. Distinct from sailing: no fleet or embark involved, so a trade route works just as well overland as along a river. Where one route's endpoint lands in the same hex as another's, they chain: you arrive, and may either ride straight on down the next one or stop there. The cost is the **drawn length of the line** (50 px = one hex = 30 mi), not the number of hexes it touches — a line that runs close to a hex boundary flickers between neighbours and can re-enter a hex it already left, which used to bill 150 miles for 90 miles of road and made fording a river look like the better option.
- Coast: draw the shoreline, then **click the side that is sea** (a preview dot follows the cursor; Shift+click an existing coast to re-pick later). Splits each crossed hex into a land part and a sea part — the line may begin or end inside a hex and it still splits. Works on land *and* sea hexes, including a Sea/Ocean hex that really holds some land or has a stronghold "on the sea". Visual, except that a coast's sea subhex counts as navigable water: any stronghold on or bordering it is a coastal port, and armies can embark/sail into it even though the hex's headline terrain is land. Fill colors are borrowed from the hex and its neighbors. Coast lines act as barriers: each coast-crossed hex is flood-filled into regions, and a region is sea only if you marked it (clicked it as sea). This means several coasts can compose into multiple sea subhexes, or two coasts can enclose an inner sea in the middle of a land hex without flooding the whole hex. While drawing, points also snap to the vertices of features you've already drawn (and, holding **E**, to any point along a drawn segment or hex edge) so new lines connect precisely to existing geometry. Alt = fully free placement.

They snap to the line *currently* being drawn too, which is what lets you draw an **island smaller than a hex**: once a coast has three points its starting node becomes a snap target (shown as a teal ring), and clicking it seals the ring and finishes the line, straight on to picking the sea side. A closed ring is flood-filled rather than split two ways, so the inside and the outside become separate subhexes; mark the outside as sea and you have an island, mark the inside and you have a pond. An *almost* closed loop leaks through the gap and gives you one broken region instead — hence the snap. Regions with holes are drawn as a single `fill-rule: evenodd` path, so the enclosing water punches a hole for the island instead of painting over it.

Coasts are **routable subhexes**, not just paint. Splitting a hex yields two (or more) co-equal regions — each land region and each sea region is its own first-class node in the movement graph (a hex can have several, e.g. two land strips separated by a sea inlet). Waypoint markers are centred on their region. Hovering highlights the exact subhex under the cursor (tinted region + "land subhex"/"sea subhex" in the tooltip). In Route mode, clicking inside a region adds a waypoint for *that* region (filled = sea, ring = land).

One hex is one hex: the cost of a hex is paid by the step that crosses *into* it, so moving between two subhexes of the same hex — a bay opening into a channel, a river mouth — is free and shows as `sail (within hex)` for 0 days. Charging a full hex again there would double-count the crossing, and a hex entered through its sea half and left from its river half must still cost exactly one hex.

Because each region is its own node, **naval subhexes block land movement**: an army can't march straight across a sea inlet — it must go around it (through connected land, possibly via a neighbouring hex) or embark at a coastal port. Marching between two land regions of adjacent hexes is only allowed where those land regions actually meet along the shared edge. The step breakdown labels each hex "Sea subhex" / "Land subhex".

**Drawn major rivers split hexes the same way**, into a region per bank, because a major river can't be forded anywhere — not even in the middle of a hex. The two banks are separate nodes: an army on one can't reach the other, or a road on the other, unless a road bridges the river inside that hex, and then the crossing is free (`bridge (within hex)`). Before this, a river that cut a hex without separating the two hex *centres* was invisible to the pathfinder, and a column could step onto a road across the water having forded nothing.
- Erase is granular: click a node to remove just that vertex, click along a segment to cut that one edge (splitting the line in two), or Shift+click to delete the whole line. Drag across the map to wipe whole features/strongholds continuously. Stronghold markers erase/reset when clicked.
- Embark/disembark only at coastal/port strongholds. Going ashore is **free**. Boarding costs +7 IRL days if you have no fleet — a month spent securing one, with the boarding folded in — or +1 IRL day if you already have ships and are simply getting back aboard after a landing. The two are never charged together. Fleets move 10 hexes/IRL day.
- Those two costs have **a checkbox each**, and they are independent. **Start as fleet** says the column owns ships, which is what licenses the 1-day re-embark; **Allow securing a fleet** licenses the 7-day month, and nothing else. A fleet with no leave to secure another may sail, land and sail again from the same dock all day, but once it marches inland its ships are gone for good. A column with neither box never takes ship at all.
- Water is only continuous where it really is continuous. **Sea to sea always connects** — the open sea and every bay along the coast are one body of water, so a coastal sea subhex sails freely to its neighbours. A **river** region, though, joins its neighbour only where the drawn major river actually goes: across a hex edge the line must cross that edge, and *within* a hex the line must run through both regions — that junction is the **river mouth**. Otherwise a bay sharing a hex with an inland channel would let a fleet step off the sea straight into the channel, anywhere along the coast, with no mouth at all.
- Docking: going ashore and re-embarking at the same port is free of the 7-day penalty (just the 1-day re-embark), but marching or trading away from the dock hex leaves the fleet behind, so re-embarking later costs the 7 days again. The calculator tracks this held-fleet state along the whole route. Port status: every sea- or river-side stronghold is a port **by default** — on, or bordering, open sea, a drawn major river, or the sea part of a coast-crossed hex — so you don't have to flag a hundred of them by hand. An explicit flag (Stronghold tool, Shift+click) always wins in either direction, which is how you carve out the exceptions. Blue-ringed markers are ports. This is deliberately looser than the river-mouth rule above: standing on the water's edge makes a port, regardless of whether a fleet can cross that particular edge. The Stronghold tool also places the marker's exact position within its hex (saved in your features JSON).
- Marker size is written as the **ratio the two sizes are meant to read as** — `SH_R = 5.1` for ordinary and fortress, and a major marker 13 to their 9 — rather than as two numbers that happen to sit near it. That is what the eye does with them: a marker is large *compared with* the ones beside it, and stating the relation is what keeps it true after a retune. The **rim** is deliberately not on that scale: an outline is a line, and a line drawn thicker to go round a larger circle stops being an edge and becomes a band; the weight difference between the two sizes is there to tell them apart at a glance, not to grow with what it encloses. The **name** keeps its own size too, being a label rather than part of the symbol, and takes a fixed clearance above the rim rather than an offset of its own, so it goes on clearing the disc whatever the disc does next. Hit-testing shares `shRadius` with the drawing, so a click inside a marker is on it whatever the grab radius happens to be at that zoom — otherwise a marker that outgrew the grab radius would look clickable and not be.
- Strongholds have a **class**, set from a hex's right-click menu: ordinary, **fortress** — the same marker at the same size, with a purple square inscribed in the white disc — or major, which is the same marker drawn larger. Size is a degree and the square is a kind, so the two are saying different things; the classes are mutually exclusive, and the setter keeps the two stored flags that way rather than trusting callers. The square is inscribed against the *inner* edge of the ring rather than the circle's radius — the stroke is painted centred on r, so corners taken out to r would sit half-buried in it — and then held to 80% of even that, because a square whose corners just reach the rim touches it at four points and reads as one blob instead of a shape inside a ring. A fraction rather than a gap in pixels, so the buffer stays in proportion when the markers are resized. Nothing in the movement rules reads any of this — it is how a place is drawn, not how it behaves.
- Strongholds can be **removed and renamed** regardless of source. The Erase tool deletes a stronghold under the cursor — including ones that come from the datasheet, which are hidden with a persistent `removed` flag in your features JSON (Ctrl+Z, or clicking the hex with the Stronghold tool, restores it). The Label tool renames any hex or stronghold (datasheet ones included); **clearing the text removes the name**, the datasheet's included, and the dialog says what the sheet called it so it can be typed back. Clearing used to mean "put the datasheet name back", which made a sheet name impossible to be rid of — hex 1953 went on calling itself Ephialtas long after its stronghold had been erased and the town redrawn a hex away — so a cleared hex now keeps an explicit blank in the features JSON, and only where there is a sheet name for it to overrule. The same erasure had a second life in the commanderies: their naming pass fell back to the datasheet whenever a hex's stronghold list came out empty, which quietly resurrected the stronghold that had just been removed and named the province after a town no longer on the map. It now asks the same function the renderer does, so what names a commandery is what you can see. Custom placements, port flags, removals and renames all live in `data/features.json`, so the datasheet snapshot is never mutated. What to call a piece of ground is now one rule in one place, asked of the **subhex**: the stronghold standing there names it, and only failing that does the hex's own label answer. The hover readout had always worked that way, but the step table and the step menu asked the hex alone — so a place whose name lives on its marker, which is every stronghold moved or added by hand, went nameless in the very list you write orders from.
